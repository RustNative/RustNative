# L6 — native backends: `rustnative-windows`, `rustnative-linux`, `rustnative-android`, `rustnative-tui` (deep read, iteration 1)

✅ = reproduced by a scratch program (`scratchpad/verify6`, run in its own console); no repository change.

L6 is about 70 000 lines. This iteration reads, in full, the paths that the L0–L5 findings and the indicators point at:
- the TUI's loop (`session.rs`), output (`encode.rs`, `grid.rs` print, `width/mod.rs`), input (`decode.rs`), restoration (`guard.rs`, `term/*` `restore_now`), services' OSC output, and `platform.rs` `run`;

- core `crash.rs` `directory`.

The remaining L6 files are queued for iteration 2 (see the ledger).

## Cross-layer confirmations

| Owed check | Result |
|---|---|
| Do backends apply only diff ops (L3-F1 impact)? | **Windows, GTK, Android: yes.** Windows `apply_operation` handles `Insert/Update/Move/Remove`, and native control state is synced only in `update_node` → `controls::update_text` → `native_controls::sync`. So a `Select` whose options change, a checkbox with overridden accessibility, or a `Foreign` whose factory kind changes stays stale on screen, because `needs_replacement` only runs on an `Update` the diff never sends. **The cursor is safe on Windows** (`cursor.rs` reads the live snapshot), and so is grid geometry (layout reads the snapshot). **The TUI is immune**: `realize_all` rebuilds its model from `view_for` every frame. L3-F1 stays P0, with impact confirmed on three of four native backends. |
| Exit-path flush (L3-F4) | **Confirmed on Windows** (`native/app.rs:155`, plus `lifecycle::notify` for `WM_QUERYENDSESSION`/suspend, which flushes and then dispatches, leaving reactions to the idle timer the OS may never fire), **GTK** (`gtk/app.rs:99`), and **Android finishing** (`lifecycle.rs` `LC_DESTROY_FINISHING`). **The TUI is not affected**: `Session::finish` flushes after `Terminating`, although it discards the flush result. |
| Headless differs from realizations (L4-F1) | Confirmed: headless and the TUI rebuild from the snapshot, while Windows, GTK, and Android apply ops, so the instrument and the product take different paths. |
| HTTP timeout, size, redirect, CRLF (L3 HTTP contract) | **Windows**: no request deadline (the WinHTTP defaults leave name resolution unlimited and allow 30 s per receive, so a slow drip never ends), an unbounded body (`read_body` grows a `Vec` until EOF), and header name/value joined with `\r\n` into `WinHttpAddRequestHeaders` (a CR/LF in a value injects extra headers). Cancelling the future does not stop the request: it runs on `spawn_blocking` to completion. **Android**: 30 s timeout. **Linux** (libsoup): its own defaults. Three backends, three timeout behaviours, and no contract-level bound. |
| `AppIdentity.id` validation (L5-F1) | State stores validate (`windows`/`linux` `for_app` reject `..`, separators, and controls). **`rustnative_core::crash::directory` does not**: `base.join(id).join("crashes")`, and it falls back to `std::env::temp_dir()` when no `LOCALAPPDATA`/`XDG_STATE_HOME`/`HOME` is set. Crash reports (which hold every `TextInput` value, L3-F5) can then land in a shared `/tmp`. |
| Android JNI panic containment | Every `RnBridge` native runs under `jni_host::guard` (`catch_unwind`), so it is contained. |

## Indicators added (L6)

- **L6.1 Contained means invisible to the host** (F1, F2): a contained panic leaves terminal modes, alternate screen, pointer capture, IME, and window state exactly as before. A pty test with `ReportAndContinue` panics, then types a key and expects it delivered in raw mode. The panic hook restores only when the panic is going to end the process (decided by the policy, not by the hook).
- **L6.2 Every backend entry point is inside a boundary that flushes** (F3): for each backend, a fault-injection test panics at render, layout, paint, measure, and service callback, and asserts that state was flushed and the host was restored.
- **L6.3 Input decoder liveness** (F4): no input sequence (including a truncated paste or an endless CSI) keeps keys from being delivered for more than `ESCAPE_TIMEOUT` + 1 s. A fuzz target over `Decoder::feed` asserts bounded memory and progress.
- **L6.4 One HTTP contract, enforced in the contract layer** (F5 and the HTTP row): `HttpRequest` validates header names and values (RFC 9110 token / field-value); `HttpService` carries a total deadline and a max response size with documented defaults. The same suite runs against every backend (a local server that stalls, drips, redirects, and sends 10 GB).
- **L6.5 Diff-consuming backends see every change** (confirmation of L3-F1): the L3.1.9 field-completeness test is run through each native backend's realization on the conformance driver, with native state read back (combobox items, checkbox state, foreign kind).

### The rest of Windows `native/`

**L6-F21 is wider than the `EDIT` echo.** These entry points also run nested window procedures while a `&mut Runtime`, `&mut WindowRegistry`, or `&mut Application` is live:

- `surfaces::choose_from_menu` runs `TrackPopupMenu`, a modal message loop, inside `with_runtime(…, tray_callback)`. Every timer, frame, deep-link, or resize message during the tray menu then resolves the same runtime again.
- `WindowRegistry::sync` (`&mut self`, or through `HostRef::with`) calls `CreateWindowExW`. Its `WM_NCCREATE`/`WM_SIZE` dispatch reaches `Runtime::sync_windows` → `registry.with(WindowRegistry::sync)`, a second `&mut WindowRegistry`. The `creating` set exists precisely because this re-entry happens. `HostRef::with`'s own safety contract forbids it.
- `poison_runtime_and_quit` makes a `&mut *runtime_ptr` in the innermost boundary, and in development builds runs `MessageBoxW` (another modal loop) while holding it.

The fix is GTK's: queue host callbacks and run them from one loop step with a `busy` flag (L6-F15), and make re-entry a checked error (`RefCell`-like) rather than an aliasing reference.
