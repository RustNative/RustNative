# Milestones 39–58 Implementation Plan (Windows backend)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan milestone-by-milestone. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take the framework from Milestone 32 to every remaining milestone in `PLAN.md` — the shared core work, Tier 0 (53, 58, 39, 40), Tier 1 (41–45), Tier 2 (46–48, 54), and Tier 3 (49–52, 55–57) — with every portable contract implemented and tested, and every host-facing half realized on the Windows backend and verified on this machine.

**Architecture:** The same two-half rule Milestones 25–32 followed (`PLAN.md` 2.4): a platform-free model in `rustnative-core` or a new platform-free crate, unit- and property-tested and exercised on the new headless reference backend (Milestone 45), then its realization in `rustnative-windows`, tested through `native::harness::NativeHarness` against real `HWND`s and the real OS API read back. Authoring (53, 58) is compile-time only — proc macros, a build-script compiler, and CLI tooling — and never reaches a backend. Server, data, sync, and durable execution (47, 49, 55, 56) are new crates on the same component, scheduler, and service contracts, verified on this Windows host as ordinary processes.

**Tech Stack:** Rust 2024 (MSRV 1.85); `syn`/`quote`/`proc-macro2` (markup and style macros); `windows`/`windows-sys` (Win32, COM, DPAPI, Shell); `serde`/`serde_json`; `hyper` + `tower` + `http` (server model — the Rust ecosystem's established service abstraction, `C37`); `rusqlite` with the bundled SQLite (server data layer, durable jobs and workflows); `argon2`, `hmac`, `sha2`, `p256` (password hashing, sessions, CSRF, passkey assertions); `clap`/`toml` (CLI).

**Spec:** `PLAN.md` §2 (principles, especially 2.9 and 2.14), §8 (backend definition of done), §9, §11 (Milestones 39–58), and `docs/ecosystem-analysis/` for the requirement identifiers each milestone cites.

## Phase A — Core work shared by the remaining targets

**Design.** Three seams PLAN §10's roadmap puts before Tier 0:

1. **Host clock.** `trait Clock: Send + Sync { fn now(&self) -> Duration; }` with `SystemClock` (monotonic, `Instant`-based) and `ManualClock` (test). `Scheduler::sleep`, `Timeline`, the persistence debounce (1.5 s), and the data layer's freshness lifetimes read time through `Services::clock()` rather than `Instant::now()` directly. `ManualExecutor` already owns a virtual time; it implements `Clock` so one test object drives both.
2. **Single-threaded executor seam.** `Executor` requires `Send + Sync` futures. Add `LocalExecutor` — `trait LocalExecutor { fn spawn_local(&self, future: Pin<Box<dyn Future<Output = ()>>>) -> ...; }` — and `LocalManualExecutor` (a `!Send` run-until-stalled executor). `Scheduler::with_local_executor` lets a component spawn a `!Send` future (`ComponentContext::spawn_local`). This is the seam a browser main thread and an embedded single-core loop need; on Windows it is exercised by a UI-thread executor pumped from the message loop (`WindowsPlatform` drains it after `pump_tasks`).
3. **`no_std`-capable subset.** New crate `rustnative-types` (`#![no_std]`, `alloc`): `Size`, `Rect`, `Point`, `EdgeInsets`, `SizeMode`, `Alignment`, `Overflow`, `Color`, the FNV key hash `NodeId::from_key` uses, and `Scalar`. `rustnative-core` re-exports them (paths unchanged). Verified by `cargo build -p rustnative-types --target thumbv7em-none-eabihf` in the gate when that target is installed (`rustup target add`), and by a `#![no_std]` doc test.

**Files:**
- Create `crates/rustnative-types/{Cargo.toml,src/lib.rs,src/geometry.rs,src/color.rs,src/hash.rs,src/scalar.rs}`.
- Create `crates/rustnative-core/src/clock.rs`; modify `scheduler/{mod.rs,executor.rs}`, `services/mod.rs` (`Services::with_clock`, `clock()`), `persistence/store.rs` (debounce reads clock), `animation/timeline.rs` if it reads `Instant`.
- Modify `crates/rustnative-core/src/layout/geometry.rs`, `style/theme.rs`, `identity.rs`, `input/pointer.rs` → re-export from `rustnative-types`.
- Modify `crates/rustnative-windows/src/native/message_loop.rs` — drain the local executor.

**Produces:**
```rust

pub struct SystemClock; pub struct ManualClock; // ManualClock::advance(Duration)
impl Clock for ManualExecutor
```

**Acceptance tests:** a `!Send` future (holding `Rc`) spawned from a component delivers its message and is cancelled on unmount; the persistence debounce flushes at exactly 1.5 s of `ManualClock` time; `rustnative-types` builds with `#![no_std]`; a Windows integration test spawns a `spawn_local` task and observes its message through the real loop.

## Milestone 45 — Test infrastructure

**Design.** A headless backend is a real `Platform`: it realizes the tree into an inspectable model through the *same* `TreeSnapshot`/`TreeDiff` path a native backend consumes, lays out with a deterministic `IntrinsicMeasurer` (fixed-advance glyph metrics, documented), and dispatches synthetic input by translating a *user action* (click at a point, type text, press a key, scroll) through hit-testing into the same `Event` values `rustnative-windows` produces — never by calling `Component::update` directly. It owns a `ManualExecutor`+`ManualClock`, so async behaviour is reproducible.

- `HeadlessBackend` — `realize(&mut Application)`, holds `HeadlessTree` (nodes with id, kind, text, geometry, resolved style, accessibility, focus, hidden, scroll offset).
- `HeadlessApp` — test driver: `click(query)`, `type_text(query, str)`, `press(KeyCode)`, `tab()`, `scroll(query, dy)`, `advance(Duration)`, `settle()` (run executor until stalled, render, re-realize), `snapshot() -> Golden`.
- **Accessibility query API (`C60`)** over the portable `AccessibilityTree`: `by_role(role).named("Submit")`, `by_label`, `by_text`, `by_state(checked)`; `get()` fails listing what the tree contains; `all()`, `exists()`.
- **Golden tests:** a stable text serialization of the realized model (`insta`-style but dependency-free: `assert_golden!(name, value)` writes `tests/goldens/<name>.golden` on `RUSTNATIVE_BLESS=1`, otherwise diffs). On Windows, visual regression captures a window with `PrintWindow` into a WIC bitmap and compares against a golden PNG with a per-channel tolerance (`rustnative-windows` test-only helper).
- **Exhaustive mode (`C11`):** `HeadlessApp::exhaustive()` — at the end of the test, any task still pending, effect registered, or outgoing message/window/animation request not consumed by an `expect_*` call fails the test with a list. Per-test overrides of clock, HTTP, storage, randomness, and any service through `Services`.
- **Lifecycle conformance suite:** process death + restoration (serialize state store, drop app, rebuild), configuration change (theme/scale/locale via environment — 39), deep link arriving during restoration, low-memory trim (`Lifecycle::LowMemory` new variant; persistence flushes, caches drop). Collisions tested as sequences.
- **Kill-and-restore test (`C14-1`)** per navigation destination (driver `kill_and_restore()`).
- **Preview-as-golden (`C55-3`)** lands with previews in 43; this milestone provides `Golden` so 43 can.
- **Device/emulator matrix, host-side device simulator, hardware-in-the-loop runner:** the matrix is a CI definition (`.github/workflows/ci.yml` job matrix: windows-latest, headless on ubuntu-latest, low-end profile = headless with a 2-core/`TokioExecutor::dedicated(1)` constraint and a scaled budget). The simulator and HIL runner belong to Milestone 37 (embedded) and are recorded as owed.

**Files:** create `crates/rustnative-headless/{Cargo.toml, src/lib.rs, src/backend.rs, src/tree.rs, src/measure.rs, src/input.rs, src/query.rs, src/golden.rs, src/exhaustive.rs, src/lifecycle.rs}`, `crates/rustnative-headless/tests/{interaction.rs, lifecycle_conformance.rs, exhaustive.rs, goldens/}`; `crates/rustnative-windows/src/native/capture.rs` (+ test); `crates/rustnative-core/src/lifecycle.rs` (`LowMemory`); `.github/workflows/ci.yml`.

**Produces:**

## Milestone 39 — Portable-surface obligations

**Design, item by item** (each item names its proving test in `docs/conformance/new-backend-checklist.md`):

1. **Desktop affordance audit + reverse audit:** `docs/conformance/portable-api-audit.md` lists window management, menus, shortcut maps, hover/cursors, drag-and-drop, multi-window state → capability (existing or new: `Cursors`, `Hover`, `ShortcutMaps`); and every Windows assumption found in core (e.g. `KeyCode` values, `WM_*`-shaped lifecycle, `Theme` default "Segoe UI", `EdgeInsets` left/right) with its resolution.
2. **Right-to-left as a layout-model property:** `LayoutDirection { Ltr, Rtl }` in the environment; `EdgeInsets` gains `start`/`end` semantics — the struct keeps `left`/`right` for physical insets and gains `EdgeInsets::logical(top, end, bottom, start)` resolved by direction; `Alignment::Start/End` already logical. `LayoutEngine::layout_with_direction` mirrors row main-axis order and horizontal insets under `Rtl`. The Windows backend applies the host's own mirroring: `WS_EX_LAYOUTRTL` on containers, `WS_EX_RTLREADING`/`ES_RIGHT` on text controls, and coordinates from the core already mirrored so the two are not double-applied (test asserts child `x` positions read back with `GetWindowRect`).
3. **Safe areas, cutouts, hinges, split-screen:** `SafeArea { insets: EdgeInsets }`, `Posture { Flat, HalfOpened { hinge: Rect }, ... }`, `WindowMode { Full, Split { fraction } }` as environment values; the layout engine applies safe-area insets to a window root marked `respects_safe_area`. Windows answers: safe area = zero, posture = flat, split = snap-layout fraction from window rect vs monitor work area.
4. **Permission states:** `PermissionState { NotAsked, Granted, Limited, Denied, PermanentlyDenied }`, `Permission` enum (Camera, Microphone, Location, Notifications, Contacts, Photos, Bluetooth), `PermissionService { state(p), request(p) -> future }`. Windows mapping documented (location/camera via the privacy registry keys `CapabilityAccessManager\ConsentStore`; notifications always granted for desktop apps).
5. **Gesture arbitration contract:** `GestureArbitration` — per node `GesturePolicy { defer_to_host, exclusive, simultaneous }`, and the enumerated conflict cases (scroll vs pan, text-selection vs drag, system-edge vs pan, long-press vs context menu) with the resolution each takes; the core `GestureRecognizer` consults it; Windows: `WM_POINTER` scroll-chaining vs pan test.
6. **Thread affinity:** `UiThread` token type (`!Send`, obtained only by a backend on its UI thread) required by the APIs that touch realized state; `debug_assert_ui_thread()` everywhere else (`ThreadAffinity::record_current()` + `assert()`), tested by calling from a worker and catching the panic in debug.
7. **One ownership module per backend:** `rustnative-windows/src/native/ownership.rs` gathers the HWND/HFONT/HBRUSH/COM ownership rules (moved from scattered module docs) with a test per rule (object counts via `GetGuiResources` before/after).
8. **Escape-hatch contract:** `NativeHandle<'ui, T>` — obtained through `Platform::native_handle(NodeId) -> Option<NativeHandle>` borrowing the `UiThread` token; invalidated by unmount (generation check); documented guarantees. Typestate (`C21`): `NativeHandle<Unchecked> → .validate() → NativeHandle<Live>`.
9. **Per-target panic and teardown policy:** `TeardownPolicy` in core (what must be restored: capture, cursor clip, fullscreen, IME, clipboard ownership, timers); Windows restores `ReleaseCapture`, `ClipCursor(null)`, exits fullscreen, kills timers, `CoUninitialize` order, on both panic and normal exit. Verified by a test that panics deliberately inside a `WNDPROC` and asserts the restored state from outside.
10. **Typed environment (`C15`):** `Environment` — typed keys `EnvKey<T>` (`THEME`, `LOCALE`, `LAYOUT_DIRECTION`, `TEXT_SCALE`, `SIZE_CLASS`, `COLOR_SCHEME`, `REDUCED_MOTION`, `CONTRAST`, `POSTURE`, `SAFE_AREA`), overridable per subtree (`ComponentContext::provide_env(key, value)` for descendants), read via `ctx.env(KEY)`, with dependency tracking so only readers of a changed key re-render (`ComponentTree::set_environment` invalidates readers only). Upward preferences: `PreferenceKey<T: Reduce>` published by a descendant via `ctx.prefer(key, v)` and reduced by an ancestor (`ctx.preference(key)`) during the next render. Windows feeds host traits: dark mode (`AppsUseLightTheme` + `WM_SETTINGCHANGE`), text scale (`TextScaleFactor` registry + `WM_SETTINGCHANGE`), reduced motion (`SPI_GETCLIENTAREAANIMATION`), contrast (`SPI_GETHIGHCONTRAST`), locale (`GetUserDefaultLocaleName`), direction from locale.
11. **Command model (`C20`):** `Command { id: CommandId, label, icon, shortcut: Option<Shortcut>, enabled, checked }`, `CommandRegistry` in the environment, `ctx.command(id, handler)`; menus (`MenuItem::command(id)`), shortcuts, buttons (`Node::with_command(id)`) bind by id; routing through the focus chain (focused component first, then ancestors, then window, then app). Windows: accelerator table built from the registry (`CreateAcceleratorTableW`, `TranslateAcceleratorW` in the loop); menu items enabled/checked from command state on `WM_INITMENUPOPUP`.
12. **Adaptive-layout vocabulary (`C22`):** `SizeClass { Compact, Medium, Expanded }` per axis with breakpoints (600/840 dp, documented); `Breakpoint` names `sm 640, md 768, lg 1024, xl 1280, 2xl 1536` (Tailwind v4 defaults, for 58's variants); computed by the layout pass from window constraints and delivered via the environment; container-relative decisions via `Node::container_query(key, |size| Node)` evaluated in a second layout pass (implemented here; 58 only defers `@container` variants).
13. **Per-property native mappers (`C24`):** Windows realization refactored so each control kind has a `MapperTable<Control>` of typed appliers (`text`, `enabled`, `font`, `colors`, `accessibility`, `opacity`…); applications extend/replace via `WindowsPlatform::mappers_mut().button.replace(Property::Text, f)` globally or `Node::with_mapper_tag("x")` per instance. The inspection protocol (44) lists active customizations (`C24-2`).
14. **Surface vocabulary (`C49-1`):** `Surface` capability enum values: `Widget, LiveActivity, Tile, Extension, InstantApp, CompanionDevice, TrayExtra, JumpList, TaskbarProgress` → added to `Capability` as `SurfaceKind` answers; Windows advertises none until 57 realizes them.
15. **Platform-group crates (`C65`):** decision recorded in `docs/conformance/platform-groups.md` (groups: `apple` = macOS+iOS, `drawlist` = terminal+embedded+overlay, `desktop-shell` shared helpers); no crate is created until a group's second member exists (the rule, not the crate, is the deliverable here).
16. **Capability grants shape (`C68`):** `Grant` (scoped: `Paths(Vec<PathBuf>)`, `Origins(Vec<String>)`, `Windows`, `Packages`), `GrantSet`, `Services::scoped(&GrantSet) -> ScopedServices` returning only granted services; `Granted<S>` typestate. Enforcement is 51.
17. **Typestate rule (`C21`):** `docs/conformance/typestate.md` + applied to `Validated<T>` (used by 47's forms), `Granted<S>`, `NativeHandle<Live>`.

**Done when** `docs/conformance/new-backend-checklist.md` exists, every item names its test, and the Windows backend passes it (plus the headless backend, for items it can answer).

## Milestone 53 — The markup syntax

**Design.**

- **`rustnative-markup`** owns the grammar: `parse_markup(TokenStream) -> Result<Markup, Diagnostics>`; AST `Element { name, attrs: Vec<Attr>, children: Vec<Child>, spread: Vec<Expr>, span }`, `Child::{Element, Expr, If, Match, For, Fragment}`; `lower(&Markup, Option<&Expr /*context*/>) -> TokenStream` (builder calls only); the **element table** — one `ElementSpec` per `Node` constructor: `Column, Row, Label, Button, TextInput, Canvas, Surface, TabBar, VirtualList` (+ any 39/48 additions), each listing its required constructor attributes (`key`, `text`/`value`/`draw_list`/`labels`+`selected`/`style`), flattened `LayoutStyle` attrs (`width height margin align_self constraints`), container attrs (`padding gap align_items overflow`), and modifier attrs (`accessibility style class input opacity transition item_index command disabled hidden`...). Unknown attribute → error naming the nearest attribute and the builder method (`did you mean `padding` (ColumnStyle::padding)?`).
- **Component elements**: a name not in the table lowers to `ctx.child_with_props::<Name, _>(key, { type P = <Name as ::rustnative_core::Component>::Props; P { attr: value, .. } }, Name::new)`; missing `in ctx,` with a component element → error at the element.
- **`rustnative-macros::rsx!`** (proc macro) = `parse_markup` + `lower`; errors as `compile_error!` with native spans.
- **`.rsx` compiler** (`rustnative_markup::rsx_file`): tokenizes the file with `proc_macro2` (`span-locations`), finds markup starts by the stated rule — `<` followed by an identifier or `>` in expression-start position (preceded by one of `= ( [ { , ; => ! & * | || && + - / % ^ == != <= >= < > : return break in` or file start inside a block) and **not** a qualified path (matching `>` followed by `::`, or `as` at depth 1) — delimits each element with the markup parser's own consumption, infers the context from the enclosing `fn`'s single `ComponentContext` parameter (none/many → error at the component element), and emits the file byte-for-byte with `::rustnative_core::rsx!(in ctx, …)` inserted around each element. Output is re-parsed with `syn::parse_file` as a check. A source map (`.rsx.map`, JSON: per line, list of `(lowered_col, source_col)` shifts) is written beside it. `mod x;` inside a `.rsx` file is rewritten to `#[path = "<abs source dir>/x.rs"] mod x;` or `rsx_mod!`-style include for `.rsx` children.
- **`rustnative_build::compile_rsx()`** walks `src/**/*.rsx`, compiles changed files into `OUT_DIR/rsx/<rel>.rs`, emits `rerun-if-changed` per file; cached by content hash.
- **`rsx_mod!(name)`** (macro_rules in core) → `#[path = concat!(env!("OUT_DIR"), "/rsx/", "name.rs")] mod name;` — `#[path]` does not accept `concat!`, so it expands to `mod name { include!(concat!(env!("OUT_DIR"), "/rsx/name.rs")); }`.
- **CLI:** `rustnative build/check/test` run Cargo with `--message-format=json-diagnostic-rendered-ansi`, remap spans in lowered files through the source map, and print rustc-style diagnostics pointing at the `.rsx`; `rustnative expand <file.rsx | file.rs>` prints builder form of every markup tree (both carriers); `rustnative fmt` formats `.rsx` files (Rust via `rustfmt` on the lowered text, markup via `rustnative_markup::format`) and `rsx!` bodies in `.rs` files; `rustnative lsp` is an LSP stdio proxy to `rust-analyzer` that maps `.rsx` URIs/positions to lowered files and back, and answers element/attribute completion and attribute hover (builder method) itself; `rustnative new --syntax builder|markup` (required, no default).
- **Test suites:** equivalence (`crates/rustnative-core/tests/syntax_equivalence.rs` + a fixture crate `tests/fixtures/rsx-equivalence` with `.rsx` files compiled by `compile_rsx`): every node kind × every modifier, builder vs `rsx!` vs `.rsx`; compile-failure suite (`trybuild` for `rsx!`; for `.rsx`, golden diagnostics from the `.rsx` compiler and from `rustnative check` on a fixture crate); expansion goldens; `.rsx` compiler tests (disambiguation cases table, context inference, byte preservation, source-map round trips, module paths).
- **Documentation obligation:** every example in `README.md`, `PLAN.md`, guides exists in both syntaxes; every runnable doc example on a public API gets a `rsx!` twin. A check (`tools/doc-syntax-check`, a test in `rustnative-core/tests/doc_parity.rs`) scans `README.md`/`PLAN.md`/`docs/guides` code fences labelled `builder`/`markup` for pairing.

## Milestone 58 — The style spellings

**Design.**

- **Model change in core (`style::decl`):** `StyleProperty` (one variant per typed property — foreground, background, border-color, border-radius, font-size, font-weight, font-family, padding-{top,end,bottom,start}, margin-*, width, height, min/max, gap, align-items, align-self, overflow, opacity, hidden…), `StyleValue { Color(Color), Length(Length), Number, Keyword, Token(TokenRef), Calc(CalcExpr) }`, `Length { Px, Rem, Em, Percent }`, `Declaration`, `Condition { State(ControlState), Scheme(ColorScheme), MinWidth(Breakpoint), Direction, ReducedMotion, PointerCoarse }`, `DeclarationSet` (`&'static [ConditionalDeclaration]` — constructed at compile time, so no runtime parse and no allocation for literals). `Theme` gains a `TokenTable` (namespaced `--color-*`, `--spacing`, `--radius-*`, `--text-*`, `--font-*`, `--shadow-*`, `--breakpoint-*`, `--ease-*`). Per-node state styles: `Node::with_state_style(ControlState, VisualStyle)` (the typed spelling of `hover:` etc.). `VisualStyle` gains the properties the vocabulary needs and does not have (`font_family` via typography, `margin` stays in layout, `opacity` already a node property).
- **Resolution:** `style::resolve::resolve_classes(node, &Theme, &Environment)` folds a node's `DeclarationSet` into its typed fields (layout, container style, visual style, state styles, opacity, hidden) with tokens resolved through the theme and conditions evaluated against the environment; run by `ComponentTree` after scoping, so a theme/scheme/size-class change re-renders → re-resolves → diffs onto existing native objects (no new HWNDs — asserted by a test counting realized objects).
- **`rustnative-style`** (platform-free, no core dependency, so the proc macro can link it): CSS value parser (lengths, colours incl. hex, `rgb()`, `hsl()`, `oklch()`, `color-mix(in oklab|srgb, …)`, `calc()`, `var()`), gamut clipping rule (oklch → linear sRGB → clamp each channel to [0,1] → gamma; documented once), the Tailwind v4 utility resolver, variants, arbitrary values, opacity modifier `/NN`, `app.css` parser (`@theme`, `@theme inline`, namespace reset `--color-*: initial`, `@utility`, `@apply`, `@custom-variant`, refusal of `@plugin`/`@config`/`@import "tailwindcss"` preflight with a diagnostic that says why), vendored default theme (`vendor/tailwind-theme-4.x.css`, MIT, pin recorded in `crates/rustnative-style/VENDORED.md`), diagnostics with byte ranges.
- **Macros:** `classes!("p-4 hover:bg-blue-500")` → `::rustnative_core::style::DeclarationSet::from_static(&[...])` (compile-time validated; spans point inside the string via `Literal::subspan` where available, otherwise the literal); `styles!("padding: 1rem; background: var(--color-primary)")` → same type. The macro reads the project's `app.css` (`CARGO_MANIFEST_DIR/app.css`, or the path in `rustnative.toml [style] file`) for project utilities/tokens and emits `include_str!` for rebuild tracking. Markup: `class="…"` → `.with_class(classes!("…"))`, `style="…"` (string) → `.with_declarations(styles!("…"))`, `style={expr}` → `.with_style(expr)`. **Documented deviation:** the builder spelling is `.with_class(classes!("…"))` rather than `.with_class("…")`, because a plain `&str` argument cannot be checked at compile time; the macro is what makes an unknown class a compile error, which 2.14's first rule requires.
- **`rustnative_build::compile_styles()`** reads `app.css`, validates it (build error with file:line:col), and writes `OUT_DIR/app_theme.rs` defining `pub fn app_theme() -> Theme` (tokens as references; inline values folded); `rustnative_core::app_theme!()` includes it.
- **Runtime token switch:** `Application::set_theme(Theme)`; Windows re-resolves and re-applies. `hello-label` gains a dark/light toggle driven by `dark:` variants and a live `ColorScheme` change from `WM_SETTINGCHANGE`.
- **Per-backend obligations:** `StyleCapabilityTable` (`fn style_capabilities(&self) -> StyleCapabilities` on `Platform`, default "unavailable" for all); Windows table: foreground/background/border colour/font realized (GDI/`WM_CTLCOLOR*`), border-radius *approximated* (containers: `SetWindowRgn` rounded region; native controls: unavailable — never owner-drawn, per 2.14 rule 4), shadow unavailable, opacity realized (layered windows, Milestone 27), gradients unavailable, transforms unavailable. Unit mapping: logical px → device px by `GetDpiForWindow/96`, `rem` = 16 px × text-scale factor (from 39's environment), rounding = round-half-away-from-zero at the boundary. Headless table: all realized (it is a model). **Build-time capability diagnostics:** `rustnative check --target windows` evaluates every `classes!`/`styles!` use in the crate (collected by the macro into `OUT_DIR/style-usage/*.json`) against the target's table and fails on an unavailable property with the span; the conformance test asserts the table against what Windows actually applies (reads back font/colour via `WM_GETFONT`/`WM_CTLCOLOR` capture).
- **CLI:** `rustnative expand` prints the declarations/typed properties a class string lowers to.
- **Suites:** style equivalence (`crates/rustnative-core/tests/style_equivalence.rs`: every documented utility and its typed spelling resolve equal); compile-fail cases (unknown class, computed class, unrealizable property on `--target windows`, bad `app.css`); colour conversion tests (oklch round trips against reference values from the Tailwind palette); unit conversion table test.

**Produces:** `style::decl::*`, `DeclarationSet`, `TokenTable`, `Node::{with_class, with_declarations, with_state_style}`, `classes!`, `styles!`, `app_theme!`, `rustnative_build::compile_styles()`, `StyleCapabilities`, `StyleSupport { Realized, Approximated(&'static str), Unavailable }`, `UnitMapping`, `Application::set_theme`.

**Done when** (PLAN 58): equivalence covers every documented property in both spellings; unknown class and unrealizable property each fail the build with a spanned diagnostic; `app.css` drives the theme with a live token switch on Windows; `expand` shows the lowering; every *shipped* backend's (Windows, headless) capability table and unit mapping recorded — deferred backends' tables owed with them; no documented style example in one spelling.

## Milestone 40 — Interoperability and incremental adoption

**Design.**

- **Embedding inward (Windows):** `WindowsPlatform::embed(parent: HWND, application) -> EmbeddedRoot` realizes a tree as a child `WS_CHILD` window inside a caller-owned HWND the framework did not create; the host's message loop drives it (`EmbeddedRoot::pump()` or subclassing the parent for `WM_SIZE`); `EmbeddedRoot::resize(Rect)`; drop tears down only our objects. Guest-runtime mode = this plus `ExternalLoop` (no `GetMessage` loop of ours).
- **Embedding outward:** `Node::foreign(key, ForeignHandle, layout)` — a new node kind (both syntaxes: `<Foreign>`), a leaf whose native object the application supplies through a `ForeignFactory` registered on the platform (`WindowsPlatform::register_foreign("chart", |parent| hwnd)`), measured through `IntrinsicMeasurer` (factory supplies preferred size), laid out/clipped by our layout, destroyed by our rules (`DestroyWindow` on unmount unless the factory says `Ownership::Borrowed`).
- **Library-only mode:** `rustnative-interop` crate — an IDL (`interface.ril`, a small typed interface description with ownership/threading annotations: `service Counter { fn increment(&mut self) -> u32 [thread=any]; event changed(u32); }`) parsed by `rustnative-interop`, generating (a) Rust `extern "C"` shims with handle tables and panic containment, (b) a C header, (c) a C# P/Invoke file — `rustnative bindgen <file.ril> --lang c|csharp|rust`. Tested by compiling the generated C with `cl.exe` (found via `vswhere`) against a `cdylib` fixture and running it (`C66`).
- **Host rendering-surface handoff:** existing `Node::native_surface` (M29) gains the documented lifetime/resize/DPI/present contract in `docs/interop/surface-handoff.md` + DPI-change test.
- **Adoption ladder:** `examples/adoption-library` (a Win32 C program calling a RustNative library-only model through the generated header — built by the test), `examples/adoption-subtree` (a plain Win32 Rust app built on `windows-sys` alone, hosting a RustNative subtree via `embed`), `examples/adoption-foreign` (a RustNative app hosting a raw `SysMonthCal32` via `Node::foreign`). Each under test.
- **Web custom element export (`C43`):** deferred with Web milestone B (recorded).

**Produces:** `EmbeddedRoot`, `ExternalLoop`, `Node::foreign`, `ForeignHandle`, `ForeignFactory`, `Ownership`, `rustnative_interop::{Idl, parse_idl, generate::{c, csharp, rust}}`, CLI `bindgen`.

**Done when** a sample pre-existing Windows application hosts a RustNative subtree, a sample RustNative application hosts a foreign control, and both are under test (Windows is the shipped native backend).

## Milestone 44 — Inspection and diagnostics

**Design.**

- **Protocol (`rustnative_core::inspect`):** serde JSON messages, versioned: `GetTree` (declarative tree), `GetRealized` (host objects + mapping, backend-supplied via `InspectBackend` trait), `GetState(ComponentPath)` / `SetState` (for components implementing `Inspectable`, a derive-free trait with `fn inspect(&self) -> serde_json::Value` and optional `fn edit(&mut self, path, value)`), `ExplainLayout(NodeId)` (constraints in, size mode, measured size, final rect, reason chain), `ExplainStyle(NodeId)` (provenance per property: token / component default / override / state variant / class — `C18-2`), `Trace { events, renders (with render-or-skip reasons, C04-2), tasks }`, `GetTasks` (scopes, tasks, owners), `GetLifetimes` (host-object create/destroy log), `GetCapabilities` (advertised, refused + reason), `GetMappers` (`C24-2`).
- **Transport:** `InspectServer` over TCP loopback (`127.0.0.1`, token-authenticated, off unless `RUSTNATIVE_INSPECT=1` or `Application::enable_inspection`), line-delimited JSON; works remotely via `--bind` (explicit, with the token). Constrained form: `inspect::compact` — deferred formatting (numeric message ids + args, host-side format table) for serial/probe transports; implemented as an encoder/decoder pair tested round trip (the embedded transport is owed with 37).
- **Inspector client:** `rustnative inspect [--addr] tree|explain <key>|state <path>|trace|tasks|caps|record|replay` — a terminal client (tables/trees).
- **In-app overlay:** `Application::set_overlay(OverlayMode::{Layout, Events, FrameCost})` → the core builds a `DrawList` of layout rectangles / event markers / frame-cost graph, realized by the backend as a topmost transparent canvas (Windows: a layered `WS_EX_TRANSPARENT` popup drawn with the existing Direct2D canvas path — no second renderer).
- **Record/replay/time travel (`C61`):** `Recorder` captures input events, messages, service responses (HTTP/storage/clock via recording service wrappers) with redaction rules (`Redact::field("password")`); `Replayer` replays deterministically on headless (and on Windows through `NativeHarness`); `StateHistory` snapshots for `Inspectable` components enable stepping back in the inspector; `rustnative inspect record → replay → to-test` converts a recording into a generated `#[test]` using `HeadlessApp`.
- **Embedded trace formats (`C92`), device sensor recordings (`C88`):** owed with 37/35/36 (recorded); the event model they would emit is the same `Trace` type.

**Done when** Windows and headless answer the protocol and the inspector ships in the CLI (terminal/embedded reduced forms owed with their backends).

## Milestone 43 — The developer loop

**Design.**

- **`rustnative dev windows`**: watches `src/`, `app.css`, `rustnative.toml`, locales; on change classifies it (Rust/`.rsx` → rebuild; `app.css` token-only change → live theme push; utility added/removed → rebuild; locale file → live catalogue push) and says which happened. Rebuild-and-restart with state preserved: the running app (dev builds link `rustnative-core`'s `dev` feature) listens on a dev channel (named pipe `\\.\pipe\rustnative-dev-<pid>`); before restart the CLI asks it to serialize (`StateStore` snapshot + navigation + window placement + `Inspectable` state) to `target/rustnative-dev/state.json`; the new process restores from it. Wall-clock time recorded to `budgets/windows.toml` (`dev_loop_restart_ms`).
- **Incremental rebuild:** template arranges the app as `app` lib crate + thin bin so an app change recompiles one crate; measured.
- **Optional dylib reload (`C59` Windows analog):** `rustnative dev --hot` builds the app crate as a `cdylib` exposing `rustnative_app_entry`, loaded by a stable host exe with `LoadLibraryW`; on change, copy-then-load the new DLL (Windows locks loaded DLLs), migrate state via the same serialize/restore path, swap the root component; falls back to restart on ABI hash mismatch.
- **On-device / board quickstart / on-demand toolchain install (`C90`):** remote-host loop works for Windows over the dev channel via TCP (`--remote host:port`, a `rustnative dev-agent` on the target copies and runs the build); phone/board quickstarts owed with 35–37. `rustnative doctor --install` offers `rustup` target/component installs (runs `rustup`, which is local tooling).
- **First-hour target:** `rustnative new app --syntax markup && cd app && rustnative run windows` — three commands; a test times it (excluding first dependency download, stated).
- **Editor assistance:** `rustnative lsp` (from 53) gains: inside `rsx!` in `.rs` files — attribute completion, hover naming the builder method, go-to-definition to the builder method (via rust-analyzer on the expanded method path); class-string completion/hover (properties a class sets, token a value references); diagnostics anchored to the class.
- **Theme editing without rebuild:** `app.css` token change pushed through the dev channel → `Application::set_theme` (58).
- **Previews and catalogue (`C55`):** `#[preview]`-free design: `rustnative_core::preview::Preview { name, render: fn(&mut ComponentContext) -> Node, matrix: PreviewMatrix }` registered via `inventory`-free explicit `previews()` functions in the app crate (`pub fn previews() -> Vec<Preview>`); `rustnative preview` renders the catalogue — on Windows as a native window listing previews with a configuration matrix (theme, locale/pseudo-locale, text scale, size class, direction, contrast), and on headless as goldens (`C55-3`: every preview is a golden test via `rustnative_headless::preview_goldens(previews())`).
- **Development services (`C58`):** resource bindings declared in `rustnative.toml [resources]` (e.g. `db = { kind = "sqlite" }`, `http_mock`), provisioned locally when absent; continuous test mode `rustnative test --watch` runs affected tests on save (crate-level affectedness); in-app error overlay: a render error / panic in dev shows an overlay window with message and source position (`.rsx` positions via the source map).
- **`rustnative generate` (`C57-1`):** `component <Name>`, `screen <Name> --route /x`, `service <Name>`, `server-resource <Name>` — each with preview and test, in the project's chosen syntax (both templates exist for each).
- **Structural editing API (`C56`):** LSP custom requests `rustnative/insertElement`, `moveElement`, `setAttribute`, `removeElement` over `.rsx` and `rsx!` trees, preserving formatting and comments outside the edited element (tests on fixtures).

**Done when** the loop's wall-clock time is in the budget file and met on Windows (device targets owed with 35–37).

## Milestone 46 — Internationalization and localization

**Design.**

- **Catalogues:** `locales/<tag>.ftl`-style files in a small documented subset of Fluent syntax (messages, `{ $arg }` placeholders, plural selectors `{ $n -> [one] … *[other] … }`, gender selectors `{ $g -> [feminine] … [masculine] … *[other] … }`, terms `-brand`, comments as translator context). Parsed by `rustnative-i18n-syntax` code inside `rustnative-style`? No — a new module `rustnative-markup::fluent`? Decision: new small platform-free crate `rustnative-i18n` (parser + plural rules CLDR data for the shipped locales: en, ar, he, pl, ru, ja, de, fr — cardinal rules encoded as functions, generated from CLDR `plurals.json`, vendored under Unicode licence).
- **Compile-time-checked placeholders:** `rustnative_build::compile_messages()` generates `OUT_DIR/messages.rs`: one typed function per message (`pub fn inbox_count(n: i64) -> Message`), missing/extra args are type errors; the macro `t!(inbox_count, n = 3)` is sugar checked against the generated function's signature. `Message` is resolved against the current locale at render time (it is data, not a string), so a locale switch re-renders readers of `LOCALE` (39 environment) only.
- **Untranslated literal lint:** `rustnative check --i18n` scans builder calls (`Node::label(_, "literal")`), `.rsx` and `rsx!` `text="literal"` attributes via `rustnative-markup`'s parser, reporting literals not wrapped in `t!` (configurable allowlist).
- **Extraction:** `rustnative i18n extract` walks `.rs` (syn), `.rsx` (markup compiler), and `rsx!` trees for `t!` uses, writes/updates `locales/<source>.ftl` with context comments (file:line); `merge` adds new keys to each translation marked `# needs-translation`, flags removed ones.
- **Locale-aware formatting delegated to the host:** `LocaleService` contract (`format_number`, `format_currency`, `format_date`, `format_time`, `format_unit`, `compare` (collation), `to_upper/lower`) — Windows via `GetNumberFormatEx`, `GetCurrencyFormatEx`, `GetDateFormatEx`/`GetTimeFormatEx`, `CompareStringEx`, `LCMapStringEx`; headless uses a documented deterministic fallback.
- **Bidi + mirroring:** joined with 39 (`LayoutDirection` from locale), utility spacing is start/end (58: `ps-`, `pe-`, `ms-`, `me-`, `start-`, `end-`; `pl-`/`pr-` remain physical and are documented as such).
- **Runtime locale switching:** `Application::set_locale` → env change → re-render readers → re-measure → Windows applies `WS_EX_LAYOUTRTL` changes to existing windows.
- **Translator workflow:** extract/merge + `rustnative i18n show <key>` (which files/screens use it) + in-app "show keys" mode (`RUSTNATIVE_I18N_SHOW_KEYS=1` renders `⟦key⟧`).
- **Pseudo-localization:** `Locale::pseudo()` (`en-XA` accented + 40 % expansion + brackets) and `ar-XB` (mirrored); wired into 41's layout conformance suite.
- **Locale-aware web routing (`C41-2`):** `Route::localized` + alternates generation in the router (portable; HTML alternates owed with Web H).
- **Example:** `examples/i18n-demo` in en, ar (RTL), pl (plural-rich), switching at runtime.

**Done when** the example ships in ar and pl, switching at runtime, with the layout suite passing under pseudo-localization on Windows and headless.

## Milestone 47 — State, resilience, and data

**Design.** Mostly in new crate `rustnative-data` (platform-free), plus core hooks.

- **Shared/scoped state (core):** `Store<T>` provided to a subtree through the environment (`ctx.provide_store(store)`), read with `ctx.store::<T>()` and **slice subscription** `ctx.select(|s: &T| s.part.clone())` (invalidated only when the selected slice changes by value — `C08`); updates via `store.update(|s| ..)` queued and applied in order at the next dispatch; **derived values** `Derived<T>` cached, recomputed when inputs change by value, visible in 44.
- **History:** `History<T>` wrapper with `undo/redo`, coalescing, bound to commands (39: `Undo`/`Redo` command ids).
- **Error boundaries + supervision (core, `C17`):** `ctx.boundary(key, policy, |ctx| child)` — a child render panic or `RenderError` in the subtree is contained: fallback node rendered, reported through 44's diagnostics channel, retried per `SupervisionPolicy { Isolate, RestartWithBackoff { initial, max, attempts }, Escalate }`; same policies on `TaskScope::supervised(policy)`; default: a child's failure does not cancel siblings.
- **Async data layer:** `QueryClient` (in `Services`), `Query<K: QueryKey, T>` with `staleTime` and `gcTime` (separate freshness/retention — `C30`), dedup of in-flight requests by key, background revalidation on focus/reconnect/mount/interval (declared `RevalidatePolicy`), retries with exponential backoff + jitter (deterministic under `ManualClock` + seeded RNG), hierarchical invalidation (`invalidate(&["todos"])`), prefetch, cancellation when unobserved, structural sharing (`Arc` reuse for unchanged subtrees of `serde_json::Value` results / `PartialEq` items), pagination/infinite queries, optimistic mutations with rollback. `ctx.query(key, fetcher) -> QueryState<T>` where `QueryState = Loading | Empty | Failure(e) | Success(T) | Refreshing(T)` (exhaustive — `C29`); colocated requirements batched by an ancestor (`BatchLoader`).
- **Offline mutation queue:** persisted in the `StateStore`, replayed on reconnect with `ConflictPolicy { ServerWins, ClientWins, Merge(fn) }`.
- **Schema migration for persisted state:** `Migrations::new().step(1, up, down)…`, `dry_run()`; `Persisted<T>` stores a version.
- **Forms (`C36`):** `Schema` derive-free builder (`field("email", text().required().email())`), `Changeset<Raw> → Result<Validated<T>, FieldErrors>`, dirty tracking, submission lifecycle (`Idle, Submitting, Succeeded, Failed`), storage-constraint errors mapped back to fields; the same `Schema` used by `rustnative-server` (49).
- **Constrained background work:** `BackgroundWork` contract with constraints (network, charging, deadline); Windows: runs when `GetSystemPowerStatus` and network (`INetworkListManager`) satisfy constraints, within the process (Windows has no process-external scheduler for desktop apps — documented).
- **Asset/image loading:** `ImageLoader` service — decode (WIC on Windows through the existing canvas path; headless: PNG via a small decoder? decision: use WIC on Windows, and for headless a test fake), downscale, memory LRU + disk cache (`%LOCALAPPDATA%/<app>/cache`), cancellation tied to component scope.
- **`C09-2`:** `ctx.prepare_off_thread(f).apply(|state, prepared| ..)` moves a large value from a worker and applies it atomically in one message.
- **`C10` state machines:** `StateMachine<S: MachineState>` with entry/exit effects tied to task scopes, `to_mermaid()` diagram generation.
- **`C12` streams:** `ctx.collect(stream, |item| Msg)` bound to the scope; suspended with it (54); hot/cold and backpressure documented per framework stream.

## Milestone 54 — Responsiveness under load

**Design (core scheduler + component tree).**

## Milestone 49 — The server application model

**Design.** New crate `rustnative-server` on `tower::Service<http::Request<Body>>` + `hyper` 1.x (server), `rusqlite` (bundled SQLite) for the reference data adapter.

- **App model on the same contracts:** `ServerApp::new().route("/users/:id", get(handler))` using core `Route` patterns; handlers are async fns with typed extractors (`Path<T>`, `Query<T>`, `Json<T>`, `Form<T>` (47 schema-validated), `Session`, `Principal<P>`, `Service<S>` request-scoped); each request runs in a request `TaskScope` cancelled at response (test: no work outlives the response — shared with 50). Middleware = tower layers. Error pages typed (`ServerError` → HTML/JSON by `Accept`).
- **Auth:** sessions (signed + encrypted cookie via HMAC-SHA256 / server-side store in SQLite), bearer tokens, password hashing (Argon2id), passkeys (WebAuthn assertion verification with `p256` ES256 over `authenticatorData || SHA256(clientDataJSON)`, registration storing COSE public keys; challenge single-use) — `C52-2`; provider federation via OAuth2 authorization-code + PKCE client (token exchange over the `HttpService` contract); **policy in types:** `Policy` trait `fn allows(principal, action, resource) -> bool` with handlers requiring `Authorized<Action, Resource>` extractors — an unauthorized route does not compile without one or an explicit `Public` marker.
- **Data layer:** `Db` pool (r2d2-free simple pool over rusqlite connections, sized), `tx(|t| ..)` transaction scoped to the request (rolled back if the request scope is cancelled); **compile-time-checked queries** via `query!("SELECT id, name FROM users WHERE id = ?", id)` proc macro that validates SQL against the schema file (`migrations/*.sql` applied to an in-memory SQLite at macro expansion) and infers the row type; migrations with up/down, dry run; generated from model changes (`C38`: `rustnative db diff` compares a declared `schema.rs` model to the migration head, emits a migration, prompts on renames, supports squash).
- **Durable jobs:** `Jobs` queue table, `enqueue(job, idempotency_key)`, workers with retries/backoff, scheduled (cron syntax subset), survives restart, inspection answering 44 (`GetJobs`).
- **Secure defaults:** CSRF (double-submit token bound to session, required on unsafe methods unless `#[csrf_exempt]`-equivalent marker), CSP with per-response nonce, `Secure; HttpOnly; SameSite=Lax` cookies, rate limiting (token bucket per IP/principal), body-size limit (1 MiB default), `Html` type whose only constructors escape (`html!`-free builder `Html::text()`, `Html::raw_trusted(&'static str)`), security headers (HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP/COEP opt-in — `C69`). Checklist `docs/server/security-checklist.md` with a test per line.
- **Admin surface:** generated from `schema.rs` models + policy: list/detail/edit/create routes with forms from the model schema, served under `/admin` and policy-gated.
- **Typed server functions:** `server_fn!`-free design: `ServerFn` trait with `const PATH`, `Input: Serialize+Deserialize`, `Output`; one definition → server handler registration + a client stub `call::<F>(http, input)` over the core `HttpService` (so the Windows app calls it). Web-milestone-H client half owed with Web.
- **Layered config:** `Config::builder().defaults(..).file("server.toml").env("APP_").secrets_dir(..)` validated at startup into a typed struct; no global; `Secret<T>` redacts on Debug and is never cached statically.
- **Mountability:** `ServerApp::into_service()` is a `tower::Service`, mountable inside an existing hyper/tower service under a path prefix, sharing listener/middleware.
- **Server-only components (`C05`):** `server_only` module gated by `cfg(feature = "server")`, boundary props `Serialize` checked at compile time; tree payload (`TreeSnapshot` JSON) merged by the ordinary reconciler on the client (the Windows client in 55's server-interactive mode). A client crate depending on a server-only item fails to compile (feature not enabled) — test via trybuild.
- **API schema (`C35`):** OpenAPI 3.1 JSON generated from routes' extractor/response types (`ApiSchema` trait impl'd for primitives/std + derive-free builder), served at `/openapi.json`; contract test fails when a published schema (`api/v1.json`) breaks compatibility.
- **`C39` data policies:** row-level policies declared next to schema, enforced for queries and subscriptions (55), fixture-driven test harness; client adapters for existing hosted backends: a generic REST adapter implementing the data-layer `QueryClient` fetcher.
- **`C40` feature-driven defaults:** pool/health (`/healthz`, `/readyz`)/metrics (`/metrics` Prometheus text)/tracing enabled by features, with a startup report of what was configured and why.
- **`C41-1` per-route metadata:** typed `Head { title, description, og, structured_data }` per route, sitemap generation, build-time validation; HTML head rendering server-side.
- **`C54-1` push sending:** Web Push (VAPID, ES256 JWT, aes128gcm payload encryption) implemented; WNS/APNs/FCM sending as adapters over the same contract, requiring credentials — implemented as request builders tested against recorded formats, not live.
- **Example:** `examples/server-demo` — authenticated, SQLite-backed, job-processing server; `examples/server-client` — the Windows app calling it through typed server functions. The "UI runs client-side, server-rendered, and serverless without modification" half is owed with Web milestones H/K.

**Done when** the example serves authenticated, database-backed, job-processing traffic, consumed by a Windows client from one codebase (web deployment modes owed with Web).

## Milestone 56 — Durable and event-driven execution

**Design.** New crate `rustnative-durable` (SQLite journal).

- **Event handlers:** `EventEnvelope { id, source, kind, time, data, attempt }`, `EventHandler` trait with batch processing returning `BatchResult { failed: Vec<EventId> }` (partial-failure reporting), retries with backoff, dead-letter table, idempotency/dedup by id, invocation-bounded task scope. Local runner (`EventRunner`) polling a queue table; serverless-platform adapters owed with Web K.
- **Durable workflows:** `Workflow` trait `async fn run(ctx: WorkflowContext, input) -> Result<Output>`; `ctx.step("name", || async {..})` records results in the journal; on restart, replay returns recorded results without re-executing; durable timers (`ctx.sleep(d)` persisted wake time), external signals (`ctx.signal::<T>("approve")`), human-approval waits, compensation (`ctx.compensate(step, undo)` run in reverse on failure), versioning (`ctx.version("change-id", min, max)`) for in-flight executions. **Determinism by type:** workflow code receives only `WorkflowContext`; time, randomness, and I/O are reachable only as `ctx.now()`, `ctx.random()`, `ctx.step()` — `WorkflowContext` does not expose the `Services`, and the `Workflow` future is required to be built from `ctx` methods (documented; enforced by the API shape — non-deterministic std calls are linted by a `clippy.toml` `disallowed-methods` list in the workflow module template and by replay divergence detection: a replayed step name/sequence mismatch fails loudly).
- **Engine adapter:** the local SQLite engine; an external engine adapter trait (`WorkflowEngine`) with the local engine as its implementation (a Temporal-style remote adapter owed with a deployment target that hosts it).
- **Stateful actors:** `Actor` trait with identity (`ActorId`), single-instance serialized execution (mailbox), private durable storage (SQLite KV per actor), alarms; `LocalActorSystem` (single-process); edge adapter owed with Web K.
- **Supervision:** 47's `SupervisionPolicy` applied to long-lived server/device processes (`Supervisor` restarts actors/workers with backoff); long-running operations (47 `Operation`) whose progress and cancellation cross client/server (server exposes operation progress over the 49 server-function channel + WebSocket).
- **Tests:** a workflow killed mid-step (process abort in a child process: the test spawns `cargo run --example workflow-crash` that aborts between steps, then resumes) completes with each step executed exactly once (side-effect counter in the DB); batch with partial failures; actor-backed collaborative session on the local system.

**Done when** the three PLAN 56 criteria hold on the local implementation (edge adapter owed with Web K).
