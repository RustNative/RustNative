# Milestone 35 Implementation Plan (the Android backend)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan phase-by-phase. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Android backend — `PLAN.md` "Milestone 35 — Android backend" — to the definition of a complete backend in `PLAN.md` §8, including the §11 gates that exist today, every Android half another milestone recorded as owed, and the Android column of `docs/conformance/new-backend-checklist.md`.

**Architecture:** One new backend crate, `rustnative-android`, plus the Java host library it ships with (`crates/rustnative-android/java/`, package `dev.rustnative.android`). The Rust runtime runs on the application's main thread — the thread Android's main `Looper` owns — exactly as the Windows and Linux runtimes run on their UI threads: every View is created, changed, measured, and destroyed synchronously from Rust through JNI, and every View callback reaches Rust through one `native` entry that posts to the backend's queue ("post, never re-enter"). JNI is confined to one ownership module (`jni_host`): global references, local frames, thread attachment, and exception checking live there and nowhere else. The tree is realized as real platform widgets (`TextView`, `Button`, `EditText`, `CheckBox`, `RadioButton`, `Switch`, `SeekBar`, `ProgressBar`, `Spinner`, …) inside framework container `ViewGroup`s (`RnLayout`) that place children exactly where the portable layout engine says; prototype views and `StaticLayout` measure; `MotionEvent`/`KeyEvent`/`InputConnection` deliver input; `AccessibilityDelegate` and `AccessibilityNodeProvider` carry the portable accessibility model; `Choreographer` paces animation; the activity lifecycle, `onSaveInstanceState`, `onTrimMemory`, and `onConfigurationChanged` drive the portable lifecycle and restoration contracts. Only platform APIs are used — no AndroidX, no Kotlin — so the host library builds from the SDK alone.

**Tech Stack:** Rust 2024 (MSRV 1.85); `jni` 0.21 (MIT/Apache, MSRV 1.65); `raw-window-handle` 0.6 and the NDK's `libandroid` (`ANativeWindow_fromSurface`) for native surfaces; Java 17 sources compiled by the Android Gradle Plugin 8.7 on Gradle 8.10.2; `compileSdk`/`targetSdk` 35, `minSdk` 26 (Android 8.0: notification channels, Keystore AES-GCM, `JobScheduler` constraints, adaptive icons). NDK r29 (`29.0.14206865`) links the four ABIs (`arm64-v8a`, `armeabi-v7a`, `x86_64`, `x86`). Verified on a physical Redmi Note 14 (Android 16, API 36, HyperOS 3, arm64) and on the Android Emulator (API 35, x86_64).

**Spec:** `PLAN.md` §2 (2.2–2.5, 2.9, 2.13, 2.14), §8 (the backend definition and Milestone 35), §11 (Milestones 39–45 and 58 gates); `docs/conformance/new-backend-checklist.md`; `docs/conformance/platform-groups.md`; `docs/conformance/permissions.md`; `docs/deploy/update-rules.md`; `docs/ecosystem-analysis/mobile.md` (`M-FP-1..3`, `M-AS-1..2`); the owed lines of `BUILD_STATUS.md` naming Milestone 35, "the mobile backends", "the deferred backends", or "the other backends".

## Global Constraints

- Everything in the 39–58 plan's Global Constraints still holds: the core stays platform-free (no `cfg(target_os)` in `rustnative-core`); MSRV 1.85; `#![deny(missing_docs)]`; clippy pedantic clean with every `#[allow]` reasoned and every `unsafe` block carrying `SAFETY:`; `cargo deny check` clean; capabilities advertised only once realized; transient interaction never renders; both syntaxes and both style spellings for anything new.
- The workspace keeps building and testing on Windows and Linux exactly as before. `rustnative-android`'s JNI dependencies are `[target.'cfg(target_os = "android")'.dependencies]`; on any other OS the crate compiles to its portable half (mapping tables, the manifest and Gradle generators' data, the unit mapping) and `AndroidPlatform::run` returns `Error::UnsupportedHost`.
- **Thread affinity.** Views are touched only on the main thread. The backend asserts it (`affinity::UiThread` plus a `Looper.myLooper() == Looper.getMainLooper()` check at entry). Services called from other threads post to the main thread through the main `Handler` and await the answer.
- **JNI discipline** (`jni_host`): every Java object Rust keeps beyond one call is a `GlobalRef` owned by exactly one Rust value; local references are bounded by `with_local_frame`; every call that can throw is followed by an exception check that clears it and converts it into `Error::Java { class, message }`; no `JNIEnv` crosses a thread; a thread that is not the main thread is attached for the duration of one call (`attach_current_thread`) or for its life (`attach_current_thread_permanently` for the service worker thread); native callbacks never unwind into the JVM (`catch_unwind` at every `extern "system"` entry).
- **No re-entrance.** A View listener never borrows backend state a render may hold: it posts, and the queue drains when no render is in progress — the same rule as Windows' message queue and Linux's GTK queue. Framework-made changes to widgets do not echo back as events (listeners are muted around them).
- **Activity lifetime is not application lifetime.** The `Application` outlives its `Activity`: a configuration change the backend handles in place, a recreation after the system destroyed the activity, and a second activity all reattach to the same application; only a finishing primary activity (or process death) ends it.
- Capability answers that differ by device (API level, a hinge, a keyboard, a stylus, Play services, TalkBack running) are computed from the running device, never from the build.

## Entry and the `run` contract

Android owns the main thread's loop (`ActivityThread` → `Looper.loop()`), and an activity's `onCreate` must return before the activity can start — so `run` cannot block there. The portable `main` stays as it is on every other host:

```rust
pub fn main() {
    let mut application = Application::new(Root::new(()), Window::new("Notes", Size::new(400, 700)));
    HostPlatform::new().run(&mut application).expect("the application ran");
}
#[cfg(target_os = "android")]
rustnative_android::export_main!(main);
```

`export_main!` exports the JNI entry the host library calls from `RnActivity.onCreate` on the main thread. `AndroidPlatform::run` **adopts** the application — it moves it out of the caller's binding with `Application::take` (a new, platform-free core method that leaves an empty application behind) into the backend's main-thread slot — attaches it to the activity, realizes the first frame, and returns `Ok(())`. From then on the main `Looper` drives it. This is documented on `AndroidPlatform::run` and in `docs/android.md`; a `run` called anywhere but inside the entry (no activity yet) returns `Error::NoActivity`. An application crate builds for Android as a library (`crate-type = ["lib"]`; `rustnative build android` asks Cargo for a `cdylib` with `cargo rustc --lib --crate-type cdylib`), so desktop builds never link a shared library they do not need.

## Verification gate

The workspace gate (`rustnative-tools/gate.sh`, on Windows) plus `rustnative-tools/gate-android.sh`:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings            # host
cargo clippy -p rustnative-android --target aarch64-linux-android -- -D warnings # device code
cargo clippy -p rustnative-android --target aarch64-linux-android --features device-tests -- -D warnings
cargo test -p rustnative-android                                                 # the portable half, on the host
cargo +1.85 check -p rustnative-android --target aarch64-linux-android
RUSTDOCFLAGS="-D warnings" cargo doc -p rustnative-android --target aarch64-linux-android --no-deps
tools/android-device-test.sh                      # instrumentation run of the device suite on every attached device
cargo deny check
```

`tools/android-device-test.sh` builds `examples/android-device-tests` (a `cdylib` with the crate's `device-tests` feature, packaged by `rustnative package android` itself), installs the APK and its instrumentation, keeps the screen on, runs `am instrument -r -w`, parses the per-test status into a pass/fail summary, and exits non-zero on any failure. Device tests are ordinary Rust functions in `crates/rustnative-android/src/device_tests/` registered in one table; each runs on the main thread inside a real activity, as the GTK harness's `on_gtk` runs on the GTK thread.

## Phase 0 — Toolchain, workspace portability, and the portable widenings

**Design.**
1. **Toolchain.** SDK at `$ANDROID_HOME` (platforms 35/36, build-tools 36.1, platform-tools, cmdline-tools), NDK r29, JDK 17 (Android Studio's JBR), Gradle 8.10.2 with `GRADLE_USER_HOME` on E:, the four Rust targets. `tools/android-env.sh` exports what a shell needs (`JAVA_HOME`, `ANDROID_NDK_HOME`, the per-target `CARGO_TARGET_*_LINKER` and `CC_*`/`AR_*` pointing at the NDK's LLVM toolchain for API 26) — the same discovery `rustnative build android` performs, so the gate and the CLI never disagree.
2. **The workspace on Android.** `cargo check --workspace --target aarch64-linux-android` for every crate the backend links, fixing whatever assumes Windows or Linux outside a cfg.
3. **Back.** `command::standard::BACK` (`rustnative.back`): a component that can go back declares it, enabled while its stack can pop (`NavigationStack::can_go_back`), and handles `Event::Command`. A backend binds the host's own back (Android's system back and predictive back, a mouse's back button, Alt+Left on Windows, the browser's history on the Web) to it. `Event::BackProgress { window, phase: BackPhase }` (`Started { edge }`, `Progressed { progress }`, `Cancelled`) lets a screen animate the predictive preview; `Committed` arrives as the command. When no component declares `BACK` enabled, the host does its own default (Android: the system's back-to-home, with its own predictive animation).
4. **Surfaces.** `SurfaceCommand::{UpdateWidget, UpdateTile, Ongoing, EndOngoing}` with portable content (`WidgetContent`: a title, lines, up to three actions; `TileState`: label, subtitle, active; `OngoingActivity`: title, body, progress, actions), each answering through `Event::SurfaceAction`. `Event::ShareReceived { window, share: SharedContent }` (text, subject, URIs with MIME types) for a share target. Every backend answers the new commands as it can and its capability says so.
5. **Style.** `rustnative_style::ANDROID`: colours, backgrounds, borders, radii, opacity, fonts (family from the system's font families and `Typeface.create`, weight, size), padding are realized on real widgets through drawables and `TextView` properties; shadows are approximated by elevation (`View.setElevation` with an outline from the radius: the host draws its own ambient and key shadow, not the declared offset/blur); everything is answered. `ANDROID_UNITS`: one logical pixel is one density-independent pixel (dp), scaled to device pixels by `DisplayMetrics.density`; `rem` is 16 dp × the system font scale; rounding half away from zero.
6. **Macros.** The unavailable-property check emits one `compile_error!` per target table under `cfg(target_os = …)`, Android included.

**Files:** `crates/rustnative-core/src/{application.rs, command.rs, event.rs, surfaces.rs}`, the other backends' surface and command handling, `crates/rustnative-style/src/capability.rs`, `crates/rustnative-macros/src/lib.rs`, `tools/android-env.sh`, `rustnative-tools/gate-android.sh`.

**Acceptance tests:** the workspace gate passes on Windows; `cargo check` for `aarch64-linux-android` and `x86_64-linux-android` builds the backend's dependency closure; `Application::take` leaves an empty application and the taken one renders identically; a stack that can pop enables `BACK` and one that cannot disables it (core test); every shipped style table answers every property (`ANDROID` included); each backend's capability test names what it answers for the new surfaces.

## Phase 1 — The crate, the JNI boundary, the host library, and the realized tree

**Design.**
- **`AndroidPlatform`** (`platform.rs`): `new()`, `run` (adopts, as above), `capabilities` (computed from the device: API level, features, Play services, a keyboard, a stylus, a hinge), `style_capabilities` → `ANDROID`, `unit_mapping` → `ANDROID_UNITS`, `native_extension`.
- **`jni_host`** (the ownership module): `Vm` (the process `JavaVM`, captured in `JNI_OnLoad`), `Env` (a main-thread `JNIEnv` borrowed for one work item), `Obj` (a `GlobalRef` with the class name it was created as, for diagnostics), `call_*` helpers that check and convert exceptions, the class cache (classes resolved once from the application's class loader, because `FindClass` on a native thread sees only the system loader), and the `extern "system"` entries of `RnBridge`. Nothing outside `jni_host` names `jni::`.
- **Host library** (`java/dev/rustnative/android/`): `RnActivity` (hosts one window: an `RnLayout` content view, lifecycle forwarding, `onBackInvokedDispatcher`, configuration changes handled in place, saved state), `RnBridge` (the `native` methods and coarse static helpers Rust calls, each one doing a whole operation — create a view of a kind, set its text, place it — so a frame is a few calls per changed node, not dozens), `RnLayout` (a `ViewGroup` that lays out each child at the rectangle Rust gave it and clips), `RnScroll` (vertical, horizontal, and two-axis scrolling with `OverScroller`, reporting offsets), the controls' listener glue, and `RnMeasure` (prototype views and `StaticLayout`).
- **Runtime** (`backend.rs`, `registry.rs`): the Linux design — one `Backend` per process on the main thread, a `WindowRegistry` mapping `Application::window_ids()` to activities, a `Work` queue every View callback posts to, drained when no work runs; the scheduler's waker posts `Work::Pump` through the main `Handler` (`Handler.post` from any thread, via `RnBridge.wake(windowId)`), and deferred work runs from `MessageQueue.addIdleHandler` so input comes first (Milestone 54).
- **Windows.** The primary window is the launching `RnActivity`. Another window opens as another `RnActivity` instance in its own task (`FLAG_ACTIVITY_NEW_DOCUMENT | FLAG_ACTIVITY_MULTIPLE_TASK`, `launchAdjacent` where the device is in multi-window), carrying its `WindowId` in the intent; a modal window is a `Dialog` over its parent's activity. `MultipleWindows` is advertised; `WindowManagement` and `WindowPlacement` are not (the host places and sizes every window).
- **Renderer** (`rendering/realization.rs`): snapshot → diff → apply → relayout, the Windows/Linux phases. Host objects: `RnLayout` for Column/Row/Grid; `RnScroll` around an `RnLayout` for `Overflow::Scroll`; `TextView` (label), `Button`, `EditText` (text input; password with `TYPE_TEXT_VARIATION_PASSWORD`), a tab bar of `RadioButton`s styled as tabs in an `RnLayout` with the tab role.
- **Measurement** (`measure.rs`): `RnMeasure` measures prototype views of each kind (`View.measure` with `AT_MOST`/`UNSPECIFIED`) so the theme's own padding and minimum sizes produce the number; labels measure through `StaticLayout` with the node's resolved `TextPaint`, wrapping within a width. Answers are cached per (kind, text, style, width) until the font scale or theme changes.
- **Device test harness** (`device_tests/`): `run_all(filter) -> Report` on the main thread; `Harness` realizes an `Application` in the test activity without the entry, pumps the queue, and exposes Views by key — the Android counterpart of `native::harness` and `gtk::testing::NativeHarness`. `RnInstrumentation` (an `android.app.Instrumentation` subclass, no AndroidX) launches `RnTestActivity`, runs the suite on the main thread, and reports each test with `sendStatus`.

**Files:** create `crates/rustnative-android/{Cargo.toml, build.rs?, src/lib.rs, src/error.rs, src/platform.rs, src/entry.rs, src/jni_host/{mod.rs, vm.rs, refs.rs, classes.rs, natives.rs}, src/backend.rs, src/registry.rs, src/rendering/{mod.rs, realization.rs, controls.rs, styling.rs}, src/measure.rs, src/device_tests/{mod.rs, harness.rs, …}, java/dev/rustnative/android/*.java}`, `examples/android-device-tests/`, `tools/android-device-test.sh`.

**Acceptance tests (on the phone and the emulator):** every basic kind realizes the View class the mapping names, at the rectangle the layout engine computed (read back from `View.getLeft/Top/Width/Height`); a performed click on a `Button` reaches `Component::update`; typing into an `EditText` produces one `TextChanged` per change and no echo on the framework's own `setText`; a scroll container scrolls without rendering; a second window opens as a second activity and closes; a modal dialog blocks its parent; the scheduler wakes the loop from another thread; the shared guarantee suites (`rustnative_conformance::suites::all`) pass on `AndroidHost`; label measurement grows with text and wraps within a width; JNI local references do not grow across 1 000 renders.

## Phase 2 — Controls, styling, host traits, environment, and direction

**Design.**
- **Controls:** Checkbox → `CheckBox`; Radio → `RadioButton` grouped per parent (exclusive through the framework, not a `RadioGroup`, which would fight the layout); Toggle → `Switch` with its label; Slider → `SeekBar` (`setMin`/`setMax`); Progress → horizontal `ProgressBar` (indeterminate while unknown); Select → `Spinner` over an `ArrayAdapter`; ListBox → an `RnLayout` of `CheckedTextView` rows in a scroll container (single choice, the list role); DatePicker → a `Button` showing the date, opening `DatePickerDialog`; Spinner (numeric) → an `RnLayout` of a decrement `Button`, a numeric `EditText`, and an increment `Button` with the spin-button role; Separator → a 1 dp `View` with the divider colour; Link → a `TextView` with the link colour and underline and the link role (activation is the application's, not the URL launcher's); MultilineText → a multi-line `EditText`; Image → `ImageView` over a `Bitmap` (`ARGB_8888`, from `ImageData`). Each raises the portable event its desktop counterparts raise, and each echo of a framework-made change is suppressed.
- **Styling** (`rendering/styling.rs`): backgrounds, borders, and radii as one `GradientDrawable` per resolved style (cached by the style's hash), wrapped in a `RippleDrawable` for pressable controls so touch feedback stays the host's; state variants (`:hover`, `:active`, `:focus-visible`, `:disabled`) as `StateListDrawable`/`ColorStateList`; text colour, font family/weight/size through `TextView`; padding through `setPadding`; opacity through `setAlpha`; hidden is `GONE`; disabled is `setEnabled(false)`; shadow as elevation with an outline provider from the radius (approximated, answered in `ANDROID`). An unstyled control keeps the device theme's own drawables — the Material (or OEM) look the person's other apps have.
- **Host traits** (`host_traits.rs`): colour scheme from `Configuration.uiMode`; text scale from `Configuration.fontScale`; contrast from `UiModeManager.getContrast()` (API 34+) and the high-text-contrast setting; reduced motion from `ValueAnimator.areAnimatorsEnabled()` and the animator duration scale; locale and direction from `Configuration.getLocales()`/`getLayoutDirection()`; accent colour from the dynamic colour palette (`android.R.color.system_accent1_*`, API 31+). Changes arrive through `onConfigurationChanged` (handled in place for `uiMode|fontScale|locale|layoutDirection|density|orientation|screenSize|smallestScreenSize|screenLayout|keyboard|keyboardHidden|navigation`), restyling existing Views without an application render unless an environment reader depends on the change.
- **Safe area, cutouts, hinges, split-screen** (`environment.rs`): edge-to-edge content (`setDecorFitsSystemWindows(false)`); `SAFE_AREA` from `WindowInsets` (system bars ∪ display cutout ∪ IME when shown, in dp); `POSTURE` from the window-extensions folding features when the device provides `androidx.window.extensions` (read reflectively from the system image; no AndroidX dependency), mapped to `HalfOpened`/`Separated` with the hinge in window coordinates; `WINDOW_MODE` from `Activity.isInMultiWindowMode()` and the window's share of the display; `SIZE_CLASS` and `WINDOW_WIDTH` from the window's current size; `POINTER` from the input devices present.
- **Direction:** the layout engine mirrors placement; `View.setLayoutDirection` and `setTextDirection` mirror what each widget draws; a runtime switch reuses the same Views.

**Acceptance tests:** every control kind realizes its widget, reports its event, and suppresses its echo; the `ANDROID` table is what the backend applies (background colour, border, radius, text colour, typeface, size, padding read back from the Views and their drawables); a night-mode switch (`UiModeManager.setApplicationNightMode` / a configuration change delivered to the activity) restyles the same Views with no application render; a font-scale change re-measures; a right-to-left locale mirrors a row and flips the Views' direction with the same objects; the safe area is the insets the window reports; `docs/components.md`'s library renders on Android.

## Phase 3 — Input

**Design.** (`input/*`)
- **Pointer:** `RnLayout.dispatchTouchEvent`/`onGenericMotionEvent` translate `MotionEvent`s — every pointer with its id, tool type (`TOOL_TYPE_FINGER` → touch, `STYLUS`/`ERASER` → pen with pressure, tilt, orientation, and the eraser flag, `MOUSE` → mouse with buttons), historical samples coalesced, hover (`ACTION_HOVER_*`), wheel (`ACTION_SCROLL` axes) — into the portable pointer model, hit-tested by the framework against laid-out nodes for nodes that declared interest, before the View under the finger sees the event.
- **Gesture arbitration with host recognizers:** a pan inside an `RnScroll` under `DeferToHost` yields to the scroll view's own touch slop and fling (the framework's recognizer cancels and the scroll view claims the sequence); a framework pan that wins calls `requestDisallowInterceptTouchEvent(true)` on its ancestors; system gesture areas (`WindowInsets.getSystemGestureInsets`) are excluded from framework edge swipes unless a node declares exclusion (`setSystemGestureExclusionRects`, bounded by the host's 200 dp limit). The conflict table is the core's (`input::arbitration`), plus the Android rows (back-gesture edges, the IME's own gestures).
- **Keys:** `Activity.dispatchKeyEvent` → `KeyCode` (`KEYCODE_*` table) and modifiers (`META_*`); key down/up; command shortcuts offered before the focused View sees the key; `Ctrl+…` shortcuts published to the system keyboard-shortcut helper (`onProvideKeyboardShortcuts`) so Meta+/ lists them.
- **IME:** native text widgets use their own `InputConnection`; a custom text target (a canvas that requested text input) gets an `RnInputView` whose `onCreateInputConnection` returns a `BaseInputConnection` delivering `setComposingText` as `Composition` and `commitText` as `TextInput`, and whose cursor rectangle is reported through `InputMethodManager.updateCursorAnchorInfo`. Showing and hiding the soft keyboard follows focus (`InputMethodManager.showSoftInput`/`hideSoftInputFromWindow`), and the IME's inset enters `SAFE_AREA`.
- **System back and predictive back:** `OnBackInvokedDispatcher.registerOnBackInvokedCallback` (API 33+) with an `OnBackAnimationCallback` (API 34+) registered exactly while the focused chain declares `BACK` enabled, so the system shows its back-to-home animation when the application has nothing to pop; `onBackStarted`/`onBackProgressed`/`onBackCancelled` become `Event::BackProgress`, `onBackInvoked` becomes `Event::Command(BACK)`. API 26–32: `onBackPressed`. `android:enableOnBackInvokedCallback="true"` in the generated manifest.
- **Clipboard:** `ClipboardManager` (text; change notifications as `ClipboardChanged`); `ClipDescription.EXTRA_IS_SENSITIVE` for content the application marks sensitive.
- **Drag and drop:** `View.OnDragListener` for text, URIs, and files (`DragEvent` with `requestDragAndDropPermissions`), with enter/over/leave/drop and effects; `View.startDragAndDrop` when a component starts a drag (`DRAG_FLAG_GLOBAL` for cross-application drags).
- **Gamepad:** `InputDevice.SOURCE_GAMEPAD|SOURCE_JOYSTICK` key and axis events into the portable `GamepadSource`; the capability is advertised only while a gamepad is connected (`InputManager.InputDeviceListener`).
- **Haptics:** the portable feedback request answered through `View.performHapticFeedback` with the host's constants.

**Acceptance tests:** the key table and the `MotionEvent` translation (recorded events: finger, stylus with pressure and tilt, mouse with buttons, hover, wheel) are pure tests on the host; on the device, `Instrumentation.sendPointerSync`/`sendKeySync` and `adb shell input` deliver real touches and keys that arrive as the portable events; a pan inside a scroll container yields to the host's scrolling; a shortcut reaches its command before a focused field; a predictive back gesture driven with `input swipe` from the edge produces `BackProgress` and then the command; with `BACK` disabled the system takes the back; the clipboard round-trips; a drop synthesized through `DragEvent` reaches the component; IME composition through a real `InputConnection`; recorded gamepad reports translate.

## Phase 4 — Accessibility through `AccessibilityNodeInfo`

**Design.** (`accessibility/*`)
- Roles: the portable `AccessibilityRole` → class name reported to services (`android.widget.Button`, `CheckBox`, `SeekBar`, `ProgressBar`, `EditText`, `ImageView`, `TabWidget`, …) and `roleDescription` where the class has no host equivalent; headings (`setHeading`), names (`contentDescription` on the View or `setText` on the node), descriptions (`setTooltipText`/hint), values (`RangeInfo` for sliders and progress, `stateDescription` for text values), states (checked, selected, expanded through actions, disabled, busy, required → `setContentInvalid`/hint, read-only), relations (`setLabelFor`/`setLabeledBy`, traversal order with `setAccessibilityTraversalBefore/After`), collections (`CollectionInfo`/`CollectionItemInfo` for lists and position in set), panes (`setAccessibilityPaneTitle` for screens), and automation ids (`setViewIdResourceName` from the node's key) — all applied through one `AccessibilityDelegate` per View driven by the portable `AccessibilityTree`, as the Windows and Linux bridges are.
- Virtual elements: an `AccessibilityNodeProvider` on the host View (a canvas, or any node with virtual children) exposes each virtual element as a virtual view with bounds, role, name, state, and actions; hover-to-explore (`dispatchHoverEvent`) finds them.
- Actions: `ACTION_CLICK`, `ACTION_LONG_CLICK`, `ACTION_SET_PROGRESS`, `ACTION_SCROLL_FORWARD/BACKWARD`, `ACTION_EXPAND/COLLAPSE`, `ACTION_SET_TEXT`, and custom actions from `AccessibleAction` raise the portable events.
- Live regions: `setAccessibilityLiveRegion(POLITE|ASSERTIVE)` on live nodes, and announcements for assertive changes.
- Verification: the device suite reads the application's own tree through `UiAutomation.getRootInActiveWindow()` — the `AccessibilityNodeInfo`s TalkBack reads — and compares roles, names, states, relations, and virtual children with `AccessibilityTree`; the same suite runs again with TalkBack enabled (`settings put secure enabled_accessibility_services`, restored after) to show the tree is served to a running screen reader and that accessibility focus moves through the declared order.

**Acceptance tests:** every role maps; a form's tree carries the roles, names, relations, and states the portable model computes; a virtual element appears with its bounds; `ACTION_CLICK` on a check box raises `Toggled`; `ACTION_SET_PROGRESS` raises `ValueChanged`; a live region's change is announced; removing a node removes its node info; TalkBack is running during the TalkBack pass.

## Phase 5 — Animation, virtual lists, canvas, native surfaces, host content

**Design.**
- **Animation:** a `Choreographer.FrameCallback` posted while anything animates evaluates the portable `Timeline` and applies frames (translation and size through the layout, opacity through `setAlpha`, colours through the style's drawable); reduced motion from the host traits.
- **Virtual lists:** the shared renderer logic — extents, anchors, ranges, recycling Views per parent and kind.
- **Canvas:** `RnCanvasView` draws a `DrawList` encoded once per change into a compact command buffer (a direct `ByteBuffer`), replayed in `onDraw` with `Path`, `Paint` (fills, strokes, linear and radial gradients), `Canvas.clipPath`, transforms, `Bitmap`s, and text through `StaticLayout`; pixel tests draw into a `Bitmap`-backed `Canvas` and read the pixels back.
- **Native surfaces:** `RnSurfaceView` (a `SurfaceView`) placed at the node's rectangle; its `Surface` becomes an `ANativeWindow` (`ANativeWindow_fromSurface`) handed out as `RawWindowHandle::AndroidNdk`; created, resized (with the density as the scale), and destroyed with its node and with the surface's own lifecycle (`surfaceCreated/Changed/Destroyed`). A test fills the window through `ANativeWindow_lock`/`unlockAndPost` and reads it back with `PixelCopy`.
- **Host content (Milestone 48):** web content through `WebView` (`Capability::WebContent`, answered from `WebView.getCurrentWebViewPackage()`); media through `VideoView` with `MediaController` (`MediaPlayback`); camera preview through Camera2 into a `TextureView` after the camera permission (`Camera`, answered from `PackageManager.FEATURE_CAMERA_ANY` and the permission's state).

**Acceptance tests:** a transition runs across frames and releases the property; reduced motion jumps to the end; a 100 000-item virtual list realizes only its window and recycles Views; canvas pixel goldens for fills, strokes, gradients, text, and clipping; a native surface's window is valid, placed, filled, resized, and released with its node; a web view loads a `data:` page and reports its title; media playback capability matches the device.

## Phase 6 — Lifecycle, system services, surfaces, and product services

**Design.**
- **Lifecycle** (`lifecycle.rs`): `onPause`/`onStop` → `Lifecycle::Suspending` (state flushed first); `onStart`/`onResume` → `Resuming`; a finishing primary `onDestroy` → `Terminating`; `onTrimMemory(TRIM_MEMORY_RUNNING_LOW|UI_HIDDEN|BACKGROUND|…)`/`onLowMemory` → `LowMemory` (the core's trim, image caches dropped); `onSaveInstanceState` flushes the `StateStore` and records a restoration marker; a cold start with saved instance state restores persisted state, navigation stacks, and the focused node before the first frame; a deep link arriving during restoration is delivered after the restored first frame (`onNewIntent` and the launch intent's `ACTION_VIEW` data → `Event::DeepLink`).
- **State store:** `FileStateStore` under `Context.getFilesDir()/rustnative/state` (atomic rename, `fsync`), present before the first render.
- **Services** (`services/*`, each `Send + Sync`, posting to the main thread where the API requires it): clipboard (above); file dialogs through the Storage Access Framework (`ACTION_OPEN_DOCUMENT`, `ACTION_CREATE_DOCUMENT`, `ACTION_OPEN_DOCUMENT_TREE`, results through `onActivityResult`, contents read through `ContentResolver`) — scoped storage, no broad storage permission; URL launch (`ACTION_VIEW`); the share sheet (`Intent.createChooser(ACTION_SEND)`); notifications with channels created from the application's declared categories (`POST_NOTIFICATIONS` asked through the permission service on API 33+), actions, and the click returning as `Event::SurfaceAction`; permissions (below); secure storage (an AES-GCM key in the Android Keystore — StrongBox where the device has it, user-authentication-bound when asked — sealing values kept in the application's private files; hardware backing answered from `KeyInfo.getSecurityLevel()`); HTTP over `HttpsURLConnection` with the system trust store and the application's network security config, certificate pins checked against the peer chain's SPKI SHA-256 before the body is read; locale through ICU (`android.icu.text.NumberFormat`, `DateFormat`, `Collator`, `CaseMap`); conditions through `ConnectivityManager` and `BatteryManager`, followed live; image decoding through `ImageDecoder` (API 28+) / `BitmapFactory`, downscaled to the requested size; printing through `PrintManager` with a `PrintDocumentAdapter` writing the application's PDF; serial ports answered unavailable (no host serial API without USB-host drivers, said so).
- **Constrained background work (`M-FP-2`):** `AndroidWork` schedules the data layer's constrained jobs with `JobScheduler` (`setRequiredNetworkType`, `setRequiresCharging`, `setOverrideDeadline`), runs them in `RnJobService` on the process's runtime (loading the library and the application's registered job handlers without an activity), and reports completion with `jobFinished`.
- **Assets (`M-FP-3`):** the data layer's image loader on Android: decode off the main thread with downscaling, a memory cache bounded by bytes (a share of `ActivityManager.getMemoryClass()`), a disk cache in `getCacheDir()`, cancellation when the requesting component unmounts, and the cache trimmed on `LowMemory`.
- **Permissions:** the portable five states — not asked, granted, limited (`READ_MEDIA_VISUAL_USER_SELECTED` on API 34+, approximate location), denied (asked, refused, may ask again: `shouldShowRequestPermissionRationale` true), permanently denied (refused with "don't ask again", or blocked by policy) — with the host's own request flow (`requestPermissions`, answered in `onRequestPermissionsResult`) behind `PermissionService::request`; the "not asked" versus "permanently denied" ambiguity Android leaves is resolved with a record of what this application asked. The mapping is documented in `docs/conformance/permissions.md`.
- **Surfaces (Milestone 57):** home-screen widgets (`RnWidgetProvider`, an `AppWidgetProvider` whose `RemoteViews` render `WidgetContent`; actions return as `Event::SurfaceAction`), a quick-settings tile (`RnTileService` rendering `TileState`, clicks as actions), share targets (an `ACTION_SEND` intent filter on `RnShareActivity` generated from `rustnative.toml`, delivering `Event::ShareReceived`), ongoing activities (an ongoing notification with progress — `SurfaceKind::LiveActivity`), launcher shortcuts (`ShortcutManager` from the jump list — `SurfaceKind::JumpList` answered as app shortcuts), and notifications. Tray and taskbar progress are answered unavailable.
- **Product services:** push through Firebase Cloud Messaging when the application ships Firebase's configuration (`RnPush`, through FCM's public classes found at run time, so no Firebase dependency is forced on applications that do not push) — otherwise `Unavailable` with the reason; a notification action's tap returns as an action; billing through Play Billing when the library is on the class path (`RnBilling`, reflected) — otherwise `Unavailable` with the reason; `FakeStore` for development; keystore-backed secure storage (above).
- **Menus:** a window's `MenuBar` realized as the activity's options menu in the action bar (`onCreateOptionsMenu`/`onPrepareOptionsMenu`, items following their commands, shortcuts shown) and context menus as `PopupMenu`.

**Acceptance tests:** on the device — `onPause`/`onResume` produce suspend and resume with state flushed first; `am kill` after backgrounding, then relaunch, restores persisted state and the navigation stack (the process-death test); a configuration change (rotation via `settings put system user_rotation`, a font-scale change) keeps the same application and the same Views; `am send-trim-memory` delivers `LowMemory`; a deep link (`am start -a VIEW -d notes://…`) during restoration lands after the restored frame; the clipboard, share sheet (intent resolved), URL launch (intent resolved), notification posted on its channel with its action, permission states read and a request flow observed through `pm grant/revoke` and `appops`, secure storage round-trips with the key in the Keystore, HTTP GET against a local server through `adb reverse`, ICU formatting and collation, conditions, image decode with downscale and cancellation, a constrained job scheduled and run by `JobScheduler` (`cmd jobscheduler run -f`), a print job's PDF produced, a widget updated (`AppWidgetManager` content read back), a tile's state, a share received through `am start -a SEND`, a launcher shortcut published, the options menu's command.

## Phase 7 — The §11 gates: inspection, embedding, developer loop, conformance, budgets

**Design.**
- **Inspection (Milestone 44):** `AndroidInspect` implements `InspectBackend` (realized Views with their class names and identity hash codes, rects, lifetimes, capabilities, style table, unit mapping); the overlay is an `RnOverlay` View drawn above the content; `RUSTNATIVE_INSPECT=1` is read from the launch intent's extras and the inspector listens on a local socket reached by `adb forward`.
- **Embedding (Milestone 40):** `RustNativeView` (a View an existing Android application puts in its own layout, or creates in code) realizes an application's primary window inside the host's activity, driven by the host's lifecycle (embedding inward); `register_foreign(kind, factory)` adopts a host `View` (created by class name or by a factory registered from Java) as a leaf, laid out and clipped by our layout (`ForeignView`, `Ownership::{Owned, Borrowed}`); **library-only mode** links the application model and services into an existing application with no UI (`RnLibrary.start(context)`), for a team adopting the data layer first.
- **Developer loop (Milestone 43) and device pairing:** `rustnative devices` lists attached devices and emulators (`adb devices -l`), `rustnative pair <host:port> <code>` pairs a device over Wi-Fi (`adb pair`), and `rustnative dev android` builds, installs, launches, forwards the dev agent's port (`adb reverse`), and reloads with state on change; `run_catalogue` shows previews on the device.
- **Conformance (Milestone 41) and lifecycle conformance (Milestone 45):** the shared suites on the device; Android-specific guarantees — host-object lifetime (live Views and global references through the registry census return to baseline after churn), fidelity (an unstyled `Button`, `EditText`, and `CheckBox` are the theme's own: same background drawable class and measured size as a plain widget), text through the host's shaper (Arabic shaping, Devanagari clusters, bidirectional ordering, fallback fonts, line breaking via `StaticLayout`), layout under font scale and pseudo-localization, modal operation (a dialog blocks its parent), panic and teardown (a deliberate panic in a handler is caught at the JNI boundary, restores pointer capture and the soft keyboard, and ends the application through its panic policy without aborting the JVM); the lifecycle suite — process death and restoration, configuration change, deep-link entry during restoration, low-memory trim.
- **Budgets (Milestone 42):** `budgets/android.toml` measured by `rustnative bench --target android` from `examples/bench-app` on the device (launch to first frame through `am start -W` and the framework's startup marks, input latency, render/tree-diff/layout microbenchmarks, idle memory from `dumpsys meminfo`, APK size), plus a low-end profile (the app pinned to one core and a reduced heap via `cmd activity set-...`/`taskset`, or a low-RAM emulator profile).

**Acceptance tests:** inspection answers `realized`/`rects`/`lifetimes`; an embedded `RustNativeView` inside a host `LinearLayout` renders and dispatches; a foreign `CalendarView` is laid out and clipped; library-only mode serves a state store and HTTP with no activity of ours; previews run; the census returns to baseline; text goldens; the lifecycle suite; `rustnative bench --target android --check` passes.

## Phase 8 — Toolchain and packaging

**Design.**
- **`rustnative-build` on Android:** from `rustnative.toml`, generates the Gradle project under `target/rustnative/android/<app>/` — `settings.gradle`, the app module's `build.gradle` (AGP 8.7, namespace from the application id, ABIs, signing config, asset packs), `AndroidManifest.xml` (application id, label, icon, version code and name, `minSdk`/`targetSdk`, the activities with their deep-link intent filters per URL scheme, the share target's filters, the widget receiver and tile service when declared, permissions from the capabilities the application uses, `enableOnBackInvokedCallback`, `configChanges`), `res/` (launcher icons at every density from the source PNG, copied at its size into `mipmap-*` with the density's directory when no larger source exists, an adaptive icon from a foreground and background when given; strings; the network security config with the certificate pins; widget provider XML), the host library's sources, and the `.so` files in `jniLibs/<abi>/`.
- **CLI:** `rustnative build android [--release] [--abi …]` (Cargo per ABI with the NDK's linker, `cargo rustc --lib --crate-type cdylib`), `rustnative run android [--device <serial>]` (build, install, launch, stream the application's log), `rustnative package android --format apk|aab|all [--sign]`: release signing with a keystore named by `RUSTNATIVE_ANDROID_KEYSTORE` (+ password variables) or `rustnative.toml`, never written into the project; a debug keystore generated with `keytool` on first use; `apksigner verify` when present; install-time asset packs declared in `rustnative.toml` assembled into the AAB. `doctor` rows: JDK, SDK and its platform/build-tools, NDK, Gradle, the Rust Android targets, `adb`, attached devices (with API level and ABI).
- **Updates (Milestone 50 on Android, the rules of `docs/deploy/update-rules.md`):** a store-installed application never updates its own code — the Play-delivered build is the update, and `AndroidUpdater` answers code updates as delegated to the store; a sideloaded build may install a signed, staged update through `PackageInstaller` sessions after the manifest's signature, version pin, and staged-rollout bucket check out, with rollback to the previous installed version kept as the fallback; data and model payloads update under both rules, fingerprint-gated (the build's fingerprint — the dependency graph, `rustnative.toml`, the generated manifest — recorded in the APK and in each payload manifest, delivery refused on mismatch) with the embedded fallback payload shipped in the APK's assets.
- **`rustnative new`:** the template gains the Android target (a `lib.rs` with `export_main!`, `crate-type`, the `[android]` section of `rustnative.toml`).

**Acceptance tests:** the manifest and Gradle files generated for a sample `rustnative.toml` (golden); `rustnative package android --format all` builds a signed APK and AAB (`apksigner verify`, `bundletool`-free inspection of the AAB's zip entries); the APK installs and launches on the phone; a byte-identical manifest on regeneration; `rustnative doctor --json` has the Android rows; `rustnative new` + `rustnative run android` launches on the phone; a data payload with a mismatched fingerprint is refused and the embedded fallback is used; a sideload update installs through a `PackageInstaller` session (with the person's confirmation, as the host requires).
