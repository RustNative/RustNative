# Milestones 25–32 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan milestone-by-milestone. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take the framework from Milestone 24 to Milestone 32 — advanced input, a real accessibility bridge, animations, virtualized lists, a custom-rendering escape hatch, persistence/navigation, the `rustnative` CLI, and Windows packaging — each realized natively on Windows and verified against real windows, not just modeled in `rustnative-core`.

**Architecture:** Every milestone lands in two halves that respect `PLAN.md` §2.4: a portable, platform-free model in `rustnative-core` (unit- and property-tested, deterministic), then its Windows realization in `rustnative-windows` (tested through `native::harness::NativeHarness` against real `HWND`s, the production message loop, and — where the milestone is about an OS service — the real OS API read back). Tooling (M31/M32) lives in new crates that orchestrate native toolchains rather than replacing them.

**Tech Stack:** Rust 2024 (MSRV 1.85), `windows-sys` for flat Win32, `windows` for COM (UIA, Direct2D, OLE drag-drop, WIC), Win32 `XInput`, `serde`/`serde_json` for persisted state, `clap`/`toml` for the CLI, Windows SDK `rc`/`mt`/`makeappx`/`signtool` for packaging.

**Spec:** `PLAN.md` §4, §6, §7 (Milestones 25–32). Milestone 33 (macOS) is explicitly **out of scope** by decision on 2026-09-19: it cannot be verified on this machine, and this project does not claim what it has not verified.

## Global Constraints

- `rustnative-core` must never depend on a platform API, and must not gain a `cfg(windows)`/`cfg(target_os)` item (`PLAN.md` §2.4).
- MSRV stays 1.85: `cargo +1.85 check --workspace --all-targets` must pass after every milestone.
- `#![deny(missing_docs)]` on every library crate; every public item documented.
- Workspace lint policy unchanged: `clippy --workspace --all-targets --all-features -- -D warnings` clean; every `#[allow]` carries a reason at its site; every `unsafe` block has a `SAFETY:` comment.
- `cargo deny check` clean: new dependencies must be MIT / Apache-2.0 / BSD-3-Clause / Unicode-3.0 compatible, no wildcard or git sources.
- A `Capability` is advertised only once realized (`capabilities_only_advertise_realized_backend_features` must be extended for every new variant).
- Transient interaction (pointer move, scroll, animation frames, hover) must never cause a component rerender (`PLAN.md` §2.10). Every milestone that touches this has a test that counts renders.
- Win32 return values are classified through `native::win32` (`must_succeed`/`best_effort`/`ignored_by_contract`/`informational`) — no bare ignored returns.
- Each milestone is complete only when: core tests + native integration tests pass on this real Windows machine; `hello-label` exercises it; `PLAN.md` moves it to "Completed" with an honest "Implemented" list; `BUILD_STATUS.md` records what was verified and what was not; one or more commits land on `master` (no push).

## Milestone 25 — Advanced input system

**Design.** Input stays semantic in the core and native in the backend. Pointer streams are opt-in per node so a busy mouse does not flood every component: a node declares `InputInterest`, and the backend only dispatches pointer/wheel/drop events to nodes (or ancestors) that asked. Gestures are recognized *in the core* from the portable pointer stream (one recognizer for every future platform, deterministically testable) rather than from `WM_GESTURE`, which is mutually exclusive with `WM_POINTER` on Windows. Pointer capture is a deferred request (same pattern as `WindowRequests`), so a component never calls into the backend mid-render.

**Files:**
- Create `crates/rustnative-core/src/input/{mod.rs,pointer.rs,gesture.rs,ime.rs,drag.rs,gamepad.rs}` — portable event payloads, `InputInterest`, `GestureRecognizer`, `DragData`, gamepad state diffing.
- Modify `crates/rustnative-core/src/event.rs` — new `Event` variants, `KeyUp`, extended `KeyCode`, `KeyModifiers::meta`.
- Modify `crates/rustnative-core/src/node.rs` — `Node::with_input(InputInterest)` stored on every node kind; `TreeNode::input`.
- Modify `crates/rustnative-core/src/component/context.rs` — `ComponentContext::input()` → `InputRequests { capture_pointer, release_pointer }`.
- Modify `crates/rustnative-core/src/capability.rs` — `Touch`, `Pen`, `Gamepad`, `Ime` capabilities.
- Create `crates/rustnative-windows/src/native/input/{mod.rs,keyboard.rs,pointer.rs,ime.rs,drop_target.rs,gamepad.rs,clipboard_watch.rs}` (the current `native/input.rs` becomes `input/keyboard.rs` + `input/focus.rs`).
- Tests: `rustnative-core/src/input/*` unit tests, `rustnative-core/tests/property_tests.rs` (gesture recognizer never panics / pan deltas sum to total), `rustnative-windows/src/native/integration.rs` new scenarios.

**Public API (Produces):**
```rust
pub enum PointerKind { Mouse, Touch, Pen }
pub enum PointerButton { Primary, Secondary, Middle, Back, Forward }
pub struct PointerEvent { pub pointer_id: u32, pub kind: PointerKind, pub position: Point /* node-local */, pub button: Option<PointerButton>, pub buttons: PointerButtons, pub modifiers: KeyModifiers, pub pressure: Option<f32> }
pub enum WheelUnit { Lines, Pixels }
pub struct WheelDelta { pub x: f32, pub y: f32, pub unit: WheelUnit }
pub enum Gesture { Tap { position: Point }, LongPress { position: Point }, Pan { delta: Point, total: Point, phase: GesturePhase }, Pinch { scale: f32, center: Point, phase: GesturePhase } }
pub enum Composition { Started, Updated { text: String, cursor: usize }, Committed { text: String }, Cancelled }
pub enum ClipboardAction { Copy, Cut, Paste { text: Option<String> } }
pub struct DragData { files: Vec<PathBuf>, text: Option<String> }  // accessors
pub enum DropEffect { None, Copy, Move, Link }
pub enum GamepadInput { Connected, Disconnected, Button { button: GamepadButton, pressed: bool }, Axis { axis: GamepadAxis, value: f32 } }
pub struct InputInterest { pointer: bool, wheel: bool, drop_target: bool, gestures: bool } // builder
// Event variants (non_exhaustive enum):
Event::PointerDown/PointerMove/PointerUp/PointerCancel { target: NodeId, pointer: PointerEvent }
Event::PointerEnter/PointerLeave { target: NodeId }
Event::Wheel { target: NodeId, delta: WheelDelta }
Event::Gesture { target: NodeId, gesture: Gesture }
Event::KeyUp { target: Option<NodeId>, key: KeyCode, modifiers: KeyModifiers }
Event::Composition { target: Option<NodeId>, composition: Composition }
Event::Clipboard { target: Option<NodeId>, action: ClipboardAction }
Event::ClipboardChanged { window: WindowId }
Event::DragEnter/DragOver { target: NodeId, data: DragData, position: Point } ; DragLeave { target } ; Drop { target, data, position }
Event::Gamepad { gamepad: u32, input: GamepadInput }
```
Components answer drag-over acceptance through `InputRequests::set_drop_effect(target, DropEffect)` read by the backend on the next `DragOver`.

**Windows realization:**
- Mouse: `WM_MOUSEMOVE`/`WM_[LRM]BUTTON{DOWN,UP}`/`WM_XBUTTON*` in `pre_dispatch` (already partially there for hover styling), mapped to node-local coordinates with `MapWindowPoints`; `WM_MOUSEHWHEEL` for horizontal wheel; precise-touchpad detection via non-`WHEEL_DELTA`-multiple deltas → `WheelUnit::Pixels`.
- Touch/pen: `WM_POINTERDOWN/UPDATE/UP/CAPTURECHANGED` + `GetPointerType`/`GetPointerPenInfo` (pressure). Mouse is *not* moved into the pointer stack (`EnableMouseInPointer` is process-global and changes standard-control behavior — rejected).
- Capture: `SetCapture`/`ReleaseCapture`; `WM_CAPTURECHANGED` → `PointerCancel`.
- Hover: `PointerEnter`/`PointerLeave` derived from the existing hover tracking (`TrackMouseEvent`).
- IME: for non-`EDIT` focus targets, `WM_IME_STARTCOMPOSITION`/`WM_IME_COMPOSITION` (`ImmGetCompositionStringW` `GCS_COMPSTR`/`GCS_RESULTSTR`/`GCS_CURSORPOS`)/`WM_IME_ENDCOMPOSITION`; native `EDIT` keeps its own IME.
- Clipboard events: Ctrl+C/X/V (and Shift+Del/Shift+Ins/Ctrl+Ins) on the focused node → `Event::Clipboard` (paste carries the clipboard text via the existing `WindowsClipboard` read path); `AddClipboardFormatListener` + `WM_CLIPBOARDUPDATE` → `ClipboardChanged`.
- Drag-and-drop: OLE `IDropTarget` implemented with `windows::core::implement`, `RegisterDragDrop` per top-level window (`OleInitialize` on the UI thread), `CF_HDROP`/`CF_UNICODETEXT` extraction; hit-test to the deepest node with `drop_target` interest. Advertise `Capability::DragAndDrop`.
- Gamepad: `XInputGetState` polled on a 16 ms `SetTimer` only while at least one window's tree has a node with gamepad interest or the root declares it; state diffing lives in the core (`GamepadState::diff`) so it is tested without a controller. XInput is loaded dynamically (`xinput1_4.dll` → `xinput9_1_0.dll`) so a machine without it degrades to "capability not advertised".

**Acceptance tests (native, real windows):** mouse down/move/up delivered with node-local coordinates to an interested node and *not* to an uninterested one; capture keeps delivering moves to the capturing node after the pointer leaves it; releasing capture delivers `PointerCancel`/stops; wheel over an interested node is delivered, over a scroll container still scrolls without rerender (render counter); `WM_POINTER*` injected via `InjectSyntheticPointerInput` (touch) when available, otherwise the test is reported skipped with the reason (never silently passed); IME composition messages drive `Composition` events; Ctrl+V on a focused button delivers `Paste` with the clipboard text set by the test; `WM_CLIPBOARDUPDATE` after a real clipboard write delivers `ClipboardChanged`; `IDropTarget::Drop` invoked in-process with a real `IDataObject` (created via `SHCreateDataObject`/`CF_HDROP`) delivers `Drop` with the file list; gamepad diffing unit tests with a fake `GamepadSource`.

## Milestone 26 — Full accessibility bridge

**Design.** Extend the portable model to the full requirement list, and build a portable `AccessibilityTree` projection in the core from a `TreeSnapshot` (roles, names, values, states, actions, relationships, live regions, set size/position for virtualized children). On Windows, implement real UI Automation providers — the audit's deferred item — rather than more annotations:
- For every HWND-backed node, a server-side `IRawElementProviderSimple` answering `WM_GETOBJECT(UiaRootObjectId)` on the control (control subclassed with `SetWindowSubclass`), with `HostRawElementProvider` = `UiaHostProviderFromHwnd` so UIA merges it with the control's own proxy, overriding only what the portable model specifies, and supplying control patterns (`Invoke`, `Value`, `RangeValue`, `Toggle`, `ExpandCollapse`, `SelectionItem`, `ScrollItem`).
- For non-HWND semantic nodes (canvas hit regions from M29, virtualized placeholders from M28), `IRawElementProviderFragment`/`FragmentRoot` children of the owning HWND's provider.
- Pattern invocations (`Invoke`, `SetValue`, `Toggle`, …) become `Event::AccessibilityAction { target, action }`, dispatched through the normal message-loop path (marshalled onto the UI thread, never mutating component state from the UIA worker thread).
- Property/structure changes raise `UiaRaiseAutomationPropertyChangedEvent`/`UiaRaiseStructureChangedEvent`; live regions raise `UiaRaiseNotificationEvent`.
The M11-era `IAccPropServices` annotation path is retired in favor of the providers (one mechanism, not two).

**Files:** `rustnative-core/src/accessibility/{mod.rs,info.rs,tree.rs,action.rs}` (moves `AccessibilityInfo`/`AccessibilityRole` out of `event.rs`, re-exported at the same paths); `rustnative-windows/src/native/uia/{mod.rs,provider.rs,fragment.rs,patterns.rs,events.rs,convert.rs}`; `rendering/accessibility.rs` becomes the adapter that drives `uia`.

**Produces:** `AccessibilityRole` gains `CheckBox, RadioButton, Slider, ProgressBar, List, ListItem, Tab, TabList, TabPanel, Heading { level: u8 }, Image, Link, Dialog, ScrollView, Canvas, Toolbar, Menu, MenuItem, Tree, TreeItem, Table, Cell, Status, Alert`; `AccessibilityInfo` gains `.value(AccessibleValue)`, `.state(AccessibleState)`, `.actions(&[AccessibleAction])`, `.labelled_by(key)`, `.described_by(key)`, `.controls(key)`, `.live(LiveRegion)`, `.set_position(index, size)`; `AccessibleValue::{Text(String), Range { min, max, current, step }}`; `AccessibleAction::{Invoke, Increment, Decrement, Expand, Collapse, Toggle, Select, SetValue(String), ScrollIntoView, Focus}`; `AccessibilityTree::from_snapshot(&TreeSnapshot) -> AccessibilityTree` with `node(id)`, `children(id)`, `resolve_relation(id, Relation)`.

**Acceptance tests:** a UIA *client* (`IUIAutomation`, run on a worker thread while the harness pumps the UI thread) reads back Name/HelpText/ControlType/IsKeyboardFocusable/Value/RangeValue/ToggleState/LabeledBy/PositionInSet/SizeOfSet from real controls; `IInvokeProvider::Invoke` and `IValueProvider::SetValue` issued by that client arrive as `Event::AccessibilityAction` in the component; a canvas region exposed as a fragment is navigable (`FindAll` by name); a live-region update raises a notification event observed by a client event handler; removing a node disconnects its provider (`UiaDisconnectProvider`) — no dangling provider after `DestroyWindow`.

## Milestone 27 — Animations and transitions

**Design.** Animation is a per-frame *native property* stream, never a rerender. The core owns the math (interpolation, easing, springs with velocity, retargeting) and a `FrameClock` abstraction; the backend owns frame delivery and property application. Two declaration forms, both declarative:
1. **Transitions** on a node: `Node::with_transition(AnimatedProperty, Transition)` — when a render changes that property, the backend interpolates from the currently displayed value to the new one; a new change mid-flight retargets from the current value and velocity (interruptible).
2. **Explicit animations** from a component: `context.animate(key, AnimationSpec)` returning an `AnimationHandle` (cancel, is_finished) owned by the component (cancelled on unmount like a task scope).
Animatable properties: `Opacity`, `Offset` (translation relative to laid-out position), `Size`, `BackgroundColor`, `ForegroundColor`. Reduced motion: `Application::motion_preference()` fed by the backend; under `Reduced`, transitions complete in one frame and explicit animations honor `AnimationSpec::reduced_motion(ReducedMotion::{Skip, Crossfade})`.

**Files:** `rustnative-core/src/animation/{mod.rs,easing.rs,spring.rs,interpolate.rs,timeline.rs,clock.rs}`; `rustnative-core/src/node.rs` (transitions); `rustnative-windows/src/native/animation.rs` (frame driver: a high-resolution waitable-timer thread posting `WM_FRAMEWORK_FRAME` only while animations are active — zero idle wakeups); `rendering/{styling.rs,realization.rs}` apply frames (`SetWindowPos` for offset/size, `WS_EX_LAYERED`+`SetLayeredWindowAttributes` for child-window opacity — requires the Windows 8+ `supportedOS` manifest entry, which the backend already needs for M32; degrade to no opacity animation without it).

**Produces:** `Easing::{Linear, EaseIn, EaseOut, EaseInOut, CubicBezier(f32,f32,f32,f32), Spring { stiffness, damping, mass }}`; `Transition { duration: Duration, easing: Easing, delay: Duration }`; `AnimatedProperty`; `AnimatedValue::{Scalar(f32), Offset(Point), Size(Size), Color(Color)}`; `Timeline::tick(now) -> Vec<PropertyFrame>`; `PropertyFrame { node: NodeId, property: AnimatedProperty, value: AnimatedValue }`; `FrameClock` trait with `ManualFrameClock` for tests; `MotionPreference::{Full, Reduced}`; `Capability::Animations`, `Capability::ReducedMotionPreference`.

**Acceptance tests:** core — easing endpoints/monotonicity (property test), spring converges and settles, retarget preserves continuity (no jump in value, velocity carried), cancellation stops frames, reduced motion completes in one tick; native — a transition on `Offset` moves the real `HWND` through intermediate positions across manual frames with **zero component renders** (render counter), final geometry equals layout; opacity frames reach `GetLayeredWindowAttributes`; the frame timer stops when the timeline is idle (no `WM_FRAMEWORK_FRAME` after settle); `SPI_GETCLIENTAREAANIMATION` false → reduced.

## Milestone 28 — Virtualized lists and large data sets

**Design.** Reuse identity, layout, scroll, and component infrastructure — no second list runtime. A `VirtualList` is a container node with an *item count*, an *extent policy*, and only the realized window of children (each keyed by its stable item key and tagged with its item index). The core computes the visible range (`VirtualRange::compute`) from scroll offset, viewport, known extents (incrementally measured) and estimates, plus overscan. The backend owns scroll offset (transient state, as today) and emits `Event::VisibleRangeChanged { target, range }` only when the *range* changes — scrolling within a range never rerenders. Scroll anchoring: the backend preserves the first visible item key + intra-item offset across inserts/removals above it. Native recycling: when one render removes and inserts controls of the same kind in a virtual list, the Windows renderer retargets the existing `HWND` (a `ControlPool`) instead of destroy+create.

**Files:** `rustnative-core/src/virtualization/{mod.rs,range.rs,extent.rs,anchor.rs}`; `node.rs` (`Node::virtual_list`, `VirtualListStyle`, `Node::item_index`); `layout/engine.rs` (virtual list layout consumes an `ExtentCache` supplied via a `LayoutInputs` struct replacing the unused `_scroll_offsets` parameter — a deliberate API change recorded in docs); `rustnative-windows/src/native/rendering/{virtual_list.rs,pool.rs}`.

**Produces:** `Node::virtual_list(key, VirtualListStyle, children)`; `VirtualListStyle { item_count: usize, extent: ItemExtent::{Fixed(u32), Estimated(u32)}, overscan: u32, axis: Axis }`; `Node::with_item_index(usize)`; `VirtualRange { first: usize, last_exclusive: usize }`; `ExtentCache` (`record(index, extent)`, `offset_of(index)`, `index_at(offset)`, `total()`) backed by a Fenwick tree for O(log n) offsets; `LayoutInputs { scroll_offsets, extents }`; accessibility `set_position`/size wired automatically (M26).

**Acceptance tests:** core — range computation property tests (visible range always covers viewport; overscan bounds; monotone in offset), Fenwick offsets equal naive prefix sums (property test), anchoring keeps the anchor item at the same viewport offset across inserts above; native — a 100,000-item list realizes ≤ (visible + 2·overscan) `HWND`s (counted via registry and `GetGuiResources(GR_USEROBJECTS)`), scrolling within a range triggers zero renders, crossing a range boundary triggers exactly one, recycled controls keep their `HWND` identity, inserting 10 items above the viewport leaves the visible content stationary; benchmark `virtual_list/range_100k` and `layout/virtual_10k` added to `core_benchmarks.rs`.

## Milestone 29 — Graphics / custom rendering escape hatch

**Design.** Two explicit, isolated paths; the default UI keeps using native controls.
1. **Canvas node** — `Node::canvas(key, DrawList)`: a retained, portable display list (shapes, paths, text, images, transforms, clips, opacity layers) diffed like any node (`Arc`-backed, pointer-equality fast path). Realized on Windows with **Direct2D** (`ID2D1HwndRenderTarget` on a dedicated child `HWND`, DirectWrite for text, `D2DERR_RECREATE_TARGET` handled by rebuilding device resources). Hit regions declared in the draw list route pointer events (M25) with a `region` id and become UIA fragments (M26).
2. **Native surface** — `Node::native_surface(key)`: a bare child `HWND` the framework positions and sizes but never paints, exposed through `raw-window-handle` 0.6 (`HasWindowHandle`/`HasDisplayHandle`) from `WindowsPlatform::surfaces()` so an application can attach its own D3D/Vulkan/wgpu swapchain. `Event::SurfaceResized { target, size, scale_factor }`.

**Files:** `rustnative-core/src/graphics/{mod.rs,draw_list.rs,path.rs,paint.rs,image.rs}`; `rustnative-windows/src/native/graphics/{mod.rs,d2d.rs,surface.rs,convert.rs}`; `rustnative-windows/src/surface.rs` (public escape-hatch API).

**Produces:** `DrawList` builder (`fill_rect`, `stroke_rect`, `fill_rounded_rect`, `fill_ellipse`, `stroke_line`, `fill_path`, `stroke_path`, `text`, `image`, `push_transform`/`pop`, `push_clip`/`pop`, `push_opacity`/`pop`, `hit_region(id, Rect)`); `Paint { color, stroke_width }`; `Path` builder; `ImageData` (RGBA8, premultiplied flag); `Transform2D`; `Event::CanvasPointer` is not a new variant — pointer events on a canvas carry `region: Option<u32>` inside `PointerEvent`; `SurfaceHandle` (Windows crate, implements `HasWindowHandle`).

**Acceptance tests:** core — draw-list equality/cheap clone, transform math, hit testing respects transforms and clip; native — render a `DrawList` through the *same* D2D translation code into a WIC bitmap render target and assert real pixel values (fill color at center, antialiased edge is intermediate, clip excludes), canvas redraw on draw-list change without other nodes rerendering, device-loss path exercised by forcing recreation, pointer on a hit region delivers the region id, `native_surface` HWND is positioned by layout and its handle round-trips through `raw-window-handle`.

## Milestone 30 — Persistence and navigation

**Design.**
- **Routes:** `Route` patterns (`/users/:id`, `*rest` wildcard) with percent-decoding and typed param access; `Router` matches a URL/path to a route name + params.
- **Navigation stack:** a core `Navigator` component (`NavigationHost`) owning a stack of entries; each entry renders its screen as a keyed child whose key is the entry's stable id, so pushing never remounts screens below. Hidden screens stay mounted but are not realized: this needs a new first-class `Node::hidden(bool)` flag (excluded from layout, focus traversal, and accessibility; realized as `ShowWindow(SW_HIDE)`). Navigation requests (`push`, `pop`, `replace`, `reset`) are deferred commands via `ComponentContext::navigator()`, applied after dispatch like window requests.
- **Tabs:** `Node::tab_bar(key, tabs, selected)` realized natively as `SysTabControl32` (`TCN_SELCHANGE` → `Event::TabSelected`), and a core `TabHost` that keeps every tab's screen mounted and shows one.
- **Deep links:** `Event::DeepLink { url }` to the primary root; `Application::open_url`. Windows: URL/argument from the command line at startup, and single-instance forwarding (named mutex + `WM_COPYDATA` to the running instance's message-only window) so a second launch hands its link to the first. Scheme registration is packaging's job (M32 MSIX `uap:Protocol`).
- **State restoration / persistent state:** `StateStore` trait (sync `load(key) -> Option<Vec<u8>>`, `save`, `remove`, `flush`) with `MemoryStateStore` in core and `FileStateStore` in Windows (`%LOCALAPPDATA%\<app-id>\state\`, atomic write via temp + `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`). Components use `context.persisted::<T: Serialize + DeserializeOwned>(key, default) -> Persisted<T>` keyed by the component's **key path** (stable across runs, unlike `ComponentId`). Lifecycle-aware: writes are buffered and flushed on `Event::Lifecycle(Suspending | Terminating)` (Windows: `WM_QUERYENDSESSION`/`WM_ENDSESSION`, `WM_POWERBROADCAST PBT_APMSUSPEND`, last-window close) and on an idle debounce. Navigation stacks and window placement (`GetWindowPlacement`/`SetWindowPlacement`) restore through the same store.

**Files:** `rustnative-core/src/navigation/{mod.rs,route.rs,navigator.rs,tabs.rs}`; `rustnative-core/src/persistence/{mod.rs,store.rs,persisted.rs,key_path.rs}`; `rustnative-core/src/lifecycle.rs`; `rustnative-windows/src/native/{single_instance.rs,lifecycle.rs}`, `rustnative-windows/src/services/state_store.rs`; `rendering/controls.rs` (tab control, hidden flag).

**Acceptance tests:** core — route matching table tests + property test (generated path round-trips through build→match), navigator push/pop preserves the lower screen's state and mount count, persisted value survives a full `Application` drop/recreate with a shared store, key path stable across reorderings; native — hidden screen's `HWND`s are invisible and skipped by Tab, tab control selection dispatches `TabSelected`, `FileStateStore` atomic write survives a simulated crash (temp file left behind is ignored/cleaned), `WM_QUERYENDSESSION` flushes, second-instance `WM_COPYDATA` delivers `DeepLink` to the first instance's root.

## Milestone 31 — Developer CLI and project tooling

**Design.** A new binary crate `crates/rustnative` (package `rustnative-cli`, binary `rustnative`) that orchestrates Cargo and the platform toolchains rather than replacing them. Project metadata lives in `rustnative.toml` (name, app id, display name, version, publisher, description, icon, url schemes, capabilities). Commands: `rustnative new <name> [--framework-path <dir>]`, `rustnative run <platform>`, `rustnative build <platform> [--release]`, `rustnative test`, `rustnative doctor [--json]`, `rustnative package <platform>` (M32). Platforms without a backend (`macos`, `linux`, `android`, `ios`, `embedded`, `web`) are recognized and fail with a specific, non-zero "no backend for <platform> yet — see PLAN.md Milestone N" error: honest, not silently mapped to Windows. `doctor` checks rustc/cargo vs MSRV, the MSVC linker (`vswhere`), Windows SDK tools (`rc`, `mt`, `makeappx`, `signtool`), `git`, and reports per-platform readiness.

**Files:** `crates/rustnative/{Cargo.toml,src/main.rs,src/cli.rs,src/config.rs,src/project/{mod.rs,templates.rs},src/toolchain/{mod.rs,windows_sdk.rs,cargo.rs},src/doctor.rs,src/platform.rs,templates/*}`; `crates/rustnative/tests/cli.rs`.

**Acceptance tests:** `rustnative new demo --framework-path <workspace>` generates a project whose `cargo check` passes (real subprocess, offline); `rustnative.toml` parse/validation errors name the field; every non-Windows platform returns the documented error and exit code; `doctor --json` is valid JSON and finds the SDK tools present on this machine; `rustnative build windows` on the generated project produces an exe.

## Milestone 32 — Packaging and deployment (Windows)

**Design.** `rustnative package windows --format zip|msix|all [--sign <pfx> --password-env VAR]`:
- **Embedded resources:** a new `rustnative-build` crate used from the app's `build.rs` (the `rustnative new` template wires it): generates an `.rc` with `VERSIONINFO` (from `rustnative.toml`/Cargo version), the application icon (`.ico`, or a `.png` wrapped into a PNG-compressed ICO entry — no image-processing dependency), and an application manifest (PerMonitorV2 DPI awareness, Common Controls v6, `supportedOS` Windows 8.1/10/11 — needed by layered child windows in M27 — UTF-8 active code page, long-path awareness), compiled with the SDK's `rc.exe` and linked via `cargo:rustc-link-arg`.
- **Portable zip:** reproducible (sorted entries, fixed timestamps, fixed permissions) plus `SHA256SUMS`.
- **MSIX:** generated `AppxManifest.xml` (identity, publisher, display name, logos, `runFullTrust`, `uap:Protocol` for each url scheme from M30), assets laid out, `makeappx pack`, optional `signtool sign /fd SHA256`. Publisher must match the certificate subject; `rustnative` checks this before calling signtool and says so.
