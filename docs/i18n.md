# Internationalization and localization

`PLAN.md` Milestone 46. The worked example is `examples/i18n-demo`. It runs in
English, Arabic (right to left), and Polish (plural-rich), and switches between
them at runtime.

## Catalogues

There is one file per locale, `locales/<tag>.ftl`, written in a documented
subset of Fluent (`rustnative-i18n`):

```text
# A comment above a message is the translator's context.
inbox-count = { $count ->
    [0] Your inbox is empty.
    [one] You have one message.
   *[other] You have { $count } messages.
}
invited = { $gender ->
    [feminine] { $name } invited you to her team.
   *[other] { $name } invited you to their team.
}
-brand = RustNative
about = About { -brand }
```

- **Plural categories** use the Unicode CLDR cardinal rules for the shipped
  languages: en, de, fr, ar (all six categories), he, pl, ru, ja, zh, and ko.
  A numeric argument picks an exact number first (`[0]`), then its category.
- **Grammatical gender**, like any other choice, is a selector on a text
  argument.
- **Fallback:** a message a locale lacks falls back to the locale's language
  (`pl` for `pl-PL`), then to the source locale. A missing message shows as
  `⟦id⟧`, so you find it on screen.

## Typed messages

`rustnative_build::compile_messages()` runs in `build.rs`. It checks every
translation against the source locale (`rustnative.toml`'s `[i18n] source`)
and generates one function per message:

```rust
rustnative_core::messages_mod!();

Node::label("count", messages::inbox_count(count))   // count: i64
Node::label("invited", messages::invited("feminine", "Ada"))
```

- A message's arguments are its function's parameters. A missing or extra
  argument is a compile error, in a builder call and in a markup attribute
  (`text={messages::inbox_count(n)}`) alike.
- A translation that reads a variable its source message is never given
  fails the build. A message missing from a translation is a warning.
- `messages::catalogues()` returns every file, embedded, for
  `Services::with_catalogues`.

## Resolution and switching

A `Message` is data. It becomes text while the component showing it renders,
against that component's `keys::LOCALE`.

- Showing a message counts as reading the locale. A locale switch therefore
  re-renders exactly the components that show messages (`C15`), and the
  controls that already exist take the new text.
- A right-to-left locale's direction (`Locale::direction`) mirrors the
  subtree it covers, on the native backend as well as the headless one.
- A catalogue can be replaced in a running application: use
  `Application::set_catalogues`, or inspection's `SetCatalogue`. That is what
  `rustnative dev` does when a `.ftl` file is saved, without a rebuild.

## Formatting

`Services::locale_service()` provides locale-aware formatting through a
`LocaleService`. On Windows that is `WindowsLocale`, which calls the
system's national-language APIs:

- `GetNumberFormatEx` for numbers;
- `GetCurrencyFormatEx` for the locale's own currency;
- `GetDateFormatEx` and `GetTimeFormatEx` for dates and times;
- `CompareStringEx` (linguistic, case-insensitive) for collation;
- `LCMapStringEx` (linguistic casing, so Turkish `i` becomes `İ`) for case.

For the person's own locale, the overrides they chose in the system's
regional settings are honored.

Windows has no API for units, or for a currency other than the locale's own.
Those are written as the locale's number followed by the unit symbol, or
preceded by the ISO code.

Without a host service, `InvariantLocale` is used. It produces the same
output on every machine: ISO dates, `,` grouping, and `.` decimals. The
headless backend uses it, so tests do not depend on the machine.

## Pseudo-localization

Two locales are pseudo-locales:

- `en-XA` accents, lengthens (+40 %), and brackets the source text.
- `ar-XB` does the same and also mirrors the layout.

They can be used in several places:

- as ordinary locales anywhere, including a preview's matrix
  (`PreviewMatrix::full`) and the catalogue's toolbar;
- in the layout conformance suite, whose reference screen is a catalogue
  resolved through the same message path. That suite runs on both backends.

With `RUSTNATIVE_I18N_SHOW_KEYS=1`, every message shows its key instead of
its text, so a translator can see where each string is.

## Routes

`Router::localized("settings", &[("en", "/settings"), ("de", "/einstellungen")])`
routes each locale's path. `Router::alternates` lists the paths in every
locale, which gives a page's language alternates. `Router::locale_of` names
the locale a path belongs to (`C41-2`).

## The translator's workflow

```sh
rustnative i18n extract      # add the messages the code uses to the source catalogue
rustnative i18n merge        # add what each translation lacks, marked # needs-translation
rustnative i18n show inbox-count
rustnative i18n lint         # literal text where a message belongs; non-zero exit for CI
```

All four commands read builder calls, `.rsx` files, and `rsx!` alike.
`[i18n] allow` lists literals that stay untranslated, such as a brand name.
